# Frontend handoff: รายงานค่าความคลาดเคลื่อน BOD/COD Online

เอกสารนี้บันทึกพฤติกรรม frontend และข้อกำหนดจากผู้ใช้สำหรับแบบรายงานผลและแบบแจ้งผล ไม่ใช่ API contract ใหม่ และไม่ได้กำหนดแนวทาง implementation ของ backend

อ้างอิง contract ปัจจุบัน: [BOD/COD deviation reports](../../docs/backend/api/menus/bod-cod-deviation-reports/README.md)

## สิทธิ์และเงื่อนไขปุ่ม

Frontend รับ `permissions.bod_cod_errors` และ `roleCodes` จากผู้ใช้ที่เข้าสู่ระบบ เพิ่มการตรวจ permission โดยคงเงื่อนไขบทบาท/สถานะเดิม ไม่เปลี่ยนเป็นใช้ permission อย่างเดียว

| ปุ่ม | เงื่อนไข frontend |
| --- | --- |
| แบบรายงานผล | `view = true` |
| แบบแจ้งผล | `view = true` และผ่านการพิจารณา; เจ้าหน้าที่ดูได้เพิ่มเติมในรอทบทวน/รออนุมัติตามเดิม |
| แก้ไข | ผู้ประกอบการ, `view/edit = true`, รอโรงงานแก้ไข ตามเดิม |
| ดำเนินการ | เจ้าหน้าที่, `view/approve = true`; ขั้นตรวจสอบต้องมี `monitoring_kpm`, `monitoring_5_centers` หรือ `admin`; รอทบทวนต้องมี `kpm_director`; รออนุมัติต้องมี `center_director` หรือ `kwp_director`; ใช้ current step และ allowedActions ล่าสุดร่วมด้วย |
| กรอกแบบแจ้งผล | เจ้าหน้าที่ที่มี `monitoring_kpm` หรือ `admin`, `view/approve = true`, `WAITING_RESULT_NOTICE` ตามเดิม |
| ยกเลิกคำขอ | ผู้ประกอบการ, `view/edit = true`, ทุกสถานะยกเว้น `APPROVED` และ `CANCELLED` |
| ม.ค.-มิ.ย. / ก.ค.-ธ.ค. | ผู้ประกอบการ หรือเจ้าหน้าที่ที่มี `admin`, `view/edit = true`, จุดตรวจวัดมี BOD/COD, อยู่ในรอบปัจจุบัน |

- ปุ่มที่ไม่เข้าเงื่อนไขยังแสดงแต่กดไม่ได้ ตามกลุ่มปุ่มผู้ประกอบการ/เจ้าหน้าที่เดิม
- การพิจารณาตรวจ `currentStep` และ `allowedActions` ร่วมกับบทบาท/สถานะ ไม่ใช้เพื่อข้ามเงื่อนไขเดิม รายละเอียดที่ไม่มี current step หรือ action ไม่ให้ดำเนินการ
- หลังโหลดรายละเอียด ตรวจสิทธิ์/สถานะอีกครั้งก่อนเปิดแก้ไขหรือดำเนินการ และมี guard ก่อนส่งข้อมูล
- เพิ่มแท็บรายชื่อโรงงานสำหรับเจ้าหน้าที่ ใช้ตาราง/รายการจุดตรวจวัดเดียวกับผู้ประกอบการ เจ้าหน้าที่ทั่วไปดูได้แต่สร้างคำขอไม่ได้
- เรียงแท็บเจ้าหน้าที่เป็น รายชื่อโรงงาน, รายการส่งแบบรายงาน, สถิติข้อมูล โดยคงแท็บเริ่มต้นเดิมไว้
- ตารางรายชื่อโรงงานและรายการส่งแบบรายงานเริ่มต้น 25 แถวต่อหน้า และมีตัวเลือก 25, 50, 100 แถว (ตารางประวัติผู้ประกอบการใช้ DataGrid เดียวกัน จึงใช้ค่าเดียวกัน)
- Admin สร้างรายงานได้ แต่ไม่ได้รับสิทธิ์ข้ามขั้นตอนทบทวน/อนุมัติด้วยบทบาท Admin เพียงอย่างเดียว
- ไม่แสดงรายการตัวอย่างแทนข้อมูลจริงเมื่อ API คืนรายการว่างหรือโหลดไม่สำเร็จ

## รอบรายงานและครั้งที่รายงาน

- ปุ่มรายงานใช้ชื่อ `ม.ค.-มิ.ย.` และ `ก.ค.-ธ.ค.` เปิดเฉพาะครึ่งปีปัจจุบันตามเขตเวลา `Asia/Bangkok`
- คำขอใหม่ตรวจปี/รอบก่อน preview และก่อนส่ง ไม่ส่งย้อนหลังหรือข้ามรอบ รวมถึงฟอร์มที่เปิดค้างข้ามรอบ
- การส่งแก้ไขคำขอเดิมข้ามครึ่งปีได้ โดยคง identity ปี รอบ และเลขครั้งเดิมตาม contract ใหม่ ไม่ใช้ validation ปี/รอบของคำขอใหม่มาบล็อก
- คำขอใหม่แสดง BOD/COD เฉพาะที่มีจริงในจุดตรวจวัดจาก factories API ส่วนการส่งแก้ไขล็อกพารามิเตอร์และตรวจ identity เดิมก่อนสร้าง payload
- รายงานได้หลายครั้งในครึ่งปี แต่คำขอเดิมของจุดตรวจวัด/พารามิเตอร์/ปีเดียวกันต้องสิ้นสุดก่อน
- Frontend โหลดรายการล่าสุดเพื่อตรวจคำขอค้างก่อน preview และก่อนส่ง หากโหลดไม่สำเร็จไม่ส่งต่อ การตรวจนี้ไม่ใช่การรับประกัน atomicity ฝั่งระบบ
- สถานะสิ้นสุดคือ `APPROVED`, `REJECTED`, `CANCELLED`; รอโรงงานแก้ไขยังเป็นคำขอค้าง
- เลขครั้งนับแยก BOD/COD ของแต่ละจุดตรวจวัดในแต่ละปี และนับต่อระหว่างสองครึ่งปี ไม่ใช่เลขรอบ 1/2
- ตัวอย่าง จุด A ปี 2569 มี COD 2 ครั้ง และ BOD 1 ครั้ง: ครั้งถัดไป COD = `3/2569`, BOD = `2/2569`
- ยกเลิกหรือไม่อนุมัติ: คำขอใหม่ของพารามิเตอร์เดิมใช้เลขครั้งเดิม การแก้ไขและส่งคำขอเดิมซ้ำไม่เพิ่มเลขครั้ง
- เลขครั้งนี้แยกจากเลขที่เอกสาร `reportNo` ไม่เปลี่ยนเลขที่เอกสารเก่า

### สถานะการรองรับเลขครั้งใน frontend

`reportRoundNo` ยังคงเป็นรอบ `1/2` ใน payload เดิม ไม่มีการเปลี่ยนเป็นเลขครั้งรายปี

Frontend แยกช่องแสดงครั้งที่ออกจากรอบแล้ว โดย adapter อ่าน `reportSequenceNo` ตาม canonical contract และแสดงคู่กับปี หากเป็น null จะแสดง `-` รวมถึง preview คำขอใหม่ที่ยังไม่บันทึก ไม่เดาจากเลขรอบหรือจำนวนแถวในตาราง และไม่ส่งเลขครั้งใน payload

การจัดสรรและการใช้เลขครั้งเดิมเป็นผลจาก API โดย frontend โหลดรายการและรายละเอียดล่าสุด ไม่จัดสรรเลขเอง

## ยกเลิกคำขอ

- คลิก **ยกเลิกคำขอ** แล้วเปิด dialog ยืนยันเฉพาะการยกเลิกคำขอ
- ปุ่มปิดฟอร์ม/ยกเลิกการกรอก/กลับ ไม่ส่งคำสั่งยกเลิกคำขอ
- เชื่อม dialog กับ `POST /api/v1/bod-cod-deviation-reports/:id/cancel` ตาม canonical contract โดยไม่ส่ง body
- ตรวจรายละเอียดล่าสุดก่อนส่ง กันการกดยืนยันซ้ำ และไม่ให้ปิด dialog ระหว่างส่ง เมื่อสำเร็จแจ้งผลและโหลดรายการรายงาน/โรงงานใหม่
- หาก error หรือ timeout จะอ่านสถานะล่าสุด ไม่ retry POST อัตโนมัติ หากอ่านสถานะไม่สำเร็จจะปิดการยืนยันจนกว่าจะเปิดข้อมูลใหม่

## การรับมือข้อมูลเปลี่ยนระหว่างกรอก

- เก็บ HTTP status, error code และ details เพื่อแยกเหตุผลของ `409 CONFLICT`
- `REPORT_PERIOD_CLOSED` สำหรับคำขอใหม่: โหลดโรงงาน/จุดตรวจวัดและรอบปัจจุบันใหม่ กลับไปให้ตรวจข้อมูลในฟอร์ม ไม่ส่งซ้ำอัตโนมัติ
- `PENDING_REPORT_EXISTS`: โหลดรายการและเปิดรายละเอียดคำขอเดิมที่ตรงจุด/พารามิเตอร์/ปี
- การส่งแก้ไขที่ conflict ใช้รายละเอียดคำขอเดิม ไม่เปลี่ยนปีหรือรอบไปเป็นรอบใหม่
- ก่อน workflow action และบันทึกแบบแจ้งผล ตรวจรายละเอียดล่าสุด หาก current step เปลี่ยน ไม่ดำเนินการข้ามขั้น

## PDF แบบรายงานผลและแบบแจ้งผล

- แสดง `เลขที่` และวันที่ยื่นคำขอจากข้อมูลจริง
- เมื่อ `APPROVED` แสดง **ผ่านการพิจารณา** ต่อจากเลขที่ ไม่แสดงจากการกดผ่านขั้นตอนก่อนอนุมัติสุดท้าย
- ครั้งที่แสดงแบบ `3/2569` แยกจากรอบครึ่งปี ไม่มีข้อมูลแสดง `-`
- ชื่อผู้รายงานในส่วนลายเซ็นใช้ `reporterName` ที่กรอกในฟอร์ม ไม่ใช้ชื่อบัญชีผู้แก้ไข และไม่เพิ่มผู้แก้ไขข้อมูลที่หัวกระดาษ
- เติมวันที่ของผู้รายงานจากวันที่ยื่นคำขอ ไม่ใช้วันที่เปิด PDF
- แบบแจ้งผลคงช่องผู้ตรวจสอบ/ผู้ทบทวน/ผู้อนุมัติเดิมไว้ ไม่มีแถวผู้รายงานและวันที่ด้านล่างสุดของเอกสาร วันที่ผู้ตรวจสอบอ่านจากเวลาบันทึกแบบแจ้งผล; วันที่อื่นที่ไม่มีข้อมูลแสดง `-`
- คงเนื้อหาและกรอบแบบฟอร์มเดิม ไม่ยกเครื่อง template
- ปรับขนาดข้อความย่อหน้าและช่องว่างบางตำแหน่งของแบบแจ้งผล เพื่อไม่ให้หมายเหตุทับช่องลายเซ็นส่วนกลาง

## API ที่ frontend ใช้ในงานนี้

| API ปัจจุบัน | การใช้งาน frontend |
| --- | --- |
| `GET /api/v1/bod-cod-deviation-reports/factories` | รายชื่อโรงงาน/จุดตรวจวัด ทั้งผู้ประกอบการและเจ้าหน้าที่ รวม Admin |
| `GET /api/v1/bod-cod-deviation-reports` | ตารางรายงาน และตรวจคำขอค้างแยกโรงงาน/จุดตรวจวัด/พารามิเตอร์/ปี |
| `GET /api/v1/bod-cod-deviation-reports/:id` | เปิด PDF, โหลดฟอร์ม, ตรวจสถานะ/สิทธิ์ดำเนินการล่าสุด |
| `POST /api/v1/bod-cod-deviation-reports` | ส่งรายงานใหม่ รวมผู้ใช้ Admin ที่มีสิทธิ์; รูปแบบ payload เดิม |
| `PUT /api/v1/bod-cod-deviation-reports/:id/resubmission` | ส่งแก้ไขคำขอเดิม; รูปแบบ payload เดิม |
| `POST /api/v1/bod-cod-deviation-reports/:id/cancel` | ยืนยันยกเลิกคำขอโดยไม่ส่ง body |
| `POST /api/v1/bod-cod-deviation-reports/attachments` | แนบไฟล์รายงานตามเดิม |
| `POST /api/v1/bod-cod-deviation-reports/:id/workflow-actions` | ขั้นตอนพิจารณาตามเดิม เพิ่ม frontend permission guard |
| `POST/PUT /api/v1/bod-cod-deviation-reports/:id/result-notice` | บันทึกแบบแจ้งผลตามเดิม เพิ่ม frontend permission guard |

ไม่มีการเปลี่ยน backend ในงาน frontend นี้ ทดสอบ frontend ด้วย mock API; ยังไม่ได้ยืนยัน migration, production deployment หรือทำคำขอจริงบน production

## การตรวจสอบ frontend

- เพิ่ม unit tests สำหรับ permission ร่วมกับบทบาท/สถานะเดิม, การยกเลิก, ขอบเขตรอบตามเวลาไทย, การตรวจคำขอค้าง และการแยกเลขครั้งออกจากเลขรอบ
- เพิ่ม integration tests สำหรับ mapping, payload รอบ 1/2 เดิม, ปุ่มยกเลิกแบบ disabled/enabled, หัวกระดาษ PDF และการสร้าง PDF ทั้งรายงาน/แจ้งผลส่วนกลาง/แจ้งผลส่วนภูมิภาค
- ตรวจ render PDF ด้วยข้อมูลทดสอบ ไม่ได้สร้างหรือเปลี่ยนคำขอจริงบน production
