# Chat: สิ่งที่ปรับใน Frontend และประเด็นแจ้ง Backend

เอกสารนี้สรุปการปรับ frontend ต่อจาก [ความต้องการเดิม](frontend-handoff-17102026.md) ไม่ใช่สัญญา API ฉบับใหม่ และไม่ยืนยันว่า backend ได้ปรับตามเงื่อนไขล่าสุดแล้ว

อ้างอิงสัญญา API ที่ [เอกสาร Chat ของ backend](../../docs/backend/api/menus/chat/README.md) รายละเอียด request, response และ error ให้ยึดเอกสารกลางดังกล่าว โดยมีประเด็นสิทธิ์เปิดเรื่องที่ต้องปรับให้ตรงกับความต้องการล่าสุดด้านล่าง

## ประเด็นสำคัญที่ Backend ต้องรับรู้

### เปิดเรื่องได้เฉพาะผู้ประกอบการ

- ผู้ประกอบการเป็นผู้เริ่มการสนทนา โดยยังต้องมีสิทธิ์ใช้งาน Chat และเข้าถึงโรงงานที่เลือก
- เจ้าหน้าที่ทุกระดับ รวมถึงผู้ดูแลระบบ ไม่สามารถเปิดเรื่องใหม่ได้ แม้มีสิทธิ์ใช้งาน Chat
- Frontend ไม่แสดงปุ่มหรือสร้าง dialog เปิดเรื่องสำหรับเจ้าหน้าที่ และป้องกันคำขอสร้าง Ticket ผ่านตัวเรียก API ของ frontend สำหรับบัญชีที่ไม่ใช่ `userType = operator`
- เจ้าหน้าที่ยังอ่าน ตอบ และปิดการสนทนาที่อยู่ในขอบเขตสิทธิ์ได้ตามเดิม การเปลี่ยนนี้ไม่ได้ถอนสิทธิ์ใช้งาน Chat ทั้งเมนู
- Frontend ยังตรวจ `canCreate` จาก API ประกอบกับประเภทผู้ใช้สำหรับการเปิดเรื่องของผู้ประกอบการ

**ขอให้ backend บังคับเงื่อนไขนี้ด้วย** ทั้งผล `canCreate` และการรับคำขอสร้าง Ticket ไม่ใช่อาศัยการป้องกันจาก frontend เท่านั้น ผู้ใช้สามารถเรียก API โดยไม่ผ่านหน้าจอได้

เอกสาร API ที่ใช้ในการพัฒนาระบุว่าเจ้าหน้าที่และผู้ดูแลเปิด Ticket ได้ จึงมีความต่างจากความต้องการล่าสุด ขอให้ backend ปรับพฤติกรรมและเอกสารกลางให้ตรงกัน โดยไม่กระทบสิทธิ์อ่าน ตอบ และปิดเรื่อง

### หัวข้อใช้ตัวเลือกจากไฟล์ใน Frontend

- ตัวเลือกหัวข้อใน dialog เปิดการสนทนาและตัวกรองหัวข้อของตารางใช้ [src/option/chatTopicOptions.json](../src/option/chatTopicOptions.json)
- ไม่ใช้ `data.topics` จาก API เป็นแหล่งตัวเลือกแล้ว
- ยังคงหัวข้อทั้ง 6 กลุ่ม และค่า `topicCode` เดิมที่ backend รองรับ ไม่มีการเพิ่มหรือเปลี่ยนรหัสหัวข้อ
- ข้อมูลหัวข้อของ Ticket ที่ backend ส่งกลับมายังใช้แสดงรายละเอียดและประวัติตามเดิม
- ยังเรียก API options เพื่อใช้ข้อมูลผู้ใช้ปัจจุบัน สิทธิ์เปิดเรื่อง และข้อจำกัดข้อความ ไม่ได้ยกเลิก endpoint นี้
- ไม่จำเป็นต้องลบ `topics` ออกจาก response ในงานนี้ หากจะเปลี่ยนชุดหัวข้อหรือรหัสในอนาคต ต้องแจ้ง frontend เพื่อปรับไฟล์ให้สอดคล้องกัน

## Dialog เปิดการสนทนา

### การเลือกโรงงาน

- ใช้รายชื่อโรงงานจาก Chat API ตามสิทธิ์บัญชีที่เข้าสู่ระบบ ไม่ใช้ข้อมูลจำลอง
- เปลี่ยนช่องเลือกโรงงานเป็นช่องที่พิมพ์ค้นหาชื่อหรือเลขทะเบียนได้ และต้องเลือกโรงงานจากรายการ ไม่รับชื่อโรงงานที่พิมพ์ขึ้นเองเป็นโรงงานใหม่
- เอาช่องค้นหาและปุ่มค้นหาแยกออก รวมถึงเลขหน้าและปุ่มก่อนหน้า/ถัดไป
- Frontend โหลดรายการโรงงานจาก API ให้ครบทุกหน้า ครั้งละ 25 รายการ แล้วค้นหาในรายการที่โหลดมา ไม่ส่งคำค้นทุกครั้งที่พิมพ์
- API ยังคงแบ่งหน้าได้ตามเดิม ไม่ต้องเปลี่ยนให้ส่งโรงงานทั้งหมดใน response เดียว และต้องกรองสิทธิ์ทุกหน้าตามเดิม
- หากบัญชีมีโรงงานจำนวนมาก จะมีหลายคำขอเพื่อโหลดให้ครบ หาก backend มีข้อจำกัดด้านจำนวนคำขอหรือปริมาณข้อมูล ขอให้แจ้งเพื่อปรับร่วมกัน

### การเลือกจุดตรวจวัด

- โหลดจุดตรวจวัดตามโรงงานที่เลือก และล้างการเลือกจุดเดิมเมื่อเปลี่ยนโรงงาน
- ตัวเลือก "ทั้งหมด" แสดงคำว่า "ทั้งหมด" ในช่อง ไม่แสดงเป็นช่องว่าง
- "ทั้งหมด" หมายถึงการเปิดเรื่องระดับโรงงาน ไม่ระบุจุดตรวจวัด โดยส่ง `measurementPoint: null` ตามเดิม ไม่ใช่รายการทุกจุด
- โรงงานที่ไม่มีจุดตรวจวัดยังเปิดเรื่องระดับโรงงานได้ ส่วนรายชื่อโรงงานยังต้องครอบคลุมโรงงานที่เข้าข่ายแต่ยังไม่เชื่อมต่อภายในสิทธิ์ของผู้ใช้ ตามความต้องการเดิม

### ข้อความแนะนำผู้ประกอบการ

เพิ่ม info panel ด้านบนของ dialog:

> เพื่อให้เจ้าหน้าที่ตรวจสอบและตอบคำถามได้รวดเร็วยิ่งขึ้น กรุณาเลือกโรงงาน จุดตรวจวัด และหัวข้อให้ตรงกับเรื่องที่ต้องการสอบถาม พร้อมอธิบายปัญหาหรือคำถามอย่างละเอียดและชัดเจน

ส่วนนี้เป็นข้อความแนะนำในหน้าจอเท่านั้น ไม่ส่งเป็นข้อความสนทนา ไม่เพิ่ม field หรือ validation ให้ backend และไม่ได้บังคับให้เลือกจุดตรวจวัดรายจุดแทน "ทั้งหมด"

## การเชื่อมต่อและพฤติกรรมที่คงไว้

- หน้า Chat เปลี่ยนจาก mockup เป็นการเรียก API สำหรับรายการ รายละเอียด ข้อความ การเปิดเรื่อง การส่งข้อความ และการปิดเรื่องแล้ว
- ตารางรายการใช้การแบ่งหน้า เรียงลำดับ และกรองผ่าน API เริ่มต้น 25 รายการ เลือกได้ 25, 50, 100
- ไม่มี polling หรือการรีเฟรชทุกช่วงเวลา ผู้ใช้รีเฟรชเองได้ และโหลดข้อมูลเมื่อเปิดการสนทนา
- ข้อความของบัญชีปัจจุบันอยู่ด้านขวา โดยเทียบตัวระบุผู้ใช้ ไม่ใช่เทียบบทบาท
- ส่งได้เฉพาะข้อความ ไม่มีไฟล์แนบหรือรูปภาพ
- ผู้มีสิทธิ์ในโรงงานหรือขอบเขตที่เกี่ยวข้องสามารถร่วมตอบและปิดเรื่องได้ ไม่จำกัดผู้เปิดเรื่อง
- ก่อนปิดเรื่องมี dialog ยืนยัน เมื่อปิดแล้วอ่านประวัติได้ แต่ส่งข้อความใหม่ไม่ได้ตามสถานะและสิทธิ์จาก backend
- การส่งซ้ำเมื่อยังไม่ทราบผลใช้ idempotency key และข้อมูลคำขอเดิม ไม่สร้างคำขอใหม่โดยอัตโนมัติ

## ขอบเขตและการตรวจสอบ

- งานนี้แก้เฉพาะ frontend ยังไม่ได้แก้ backend
- จุดที่ต้องปรับฝั่ง backend คือสิทธิ์เริ่มการสนทนาให้เป็นผู้ประกอบการเท่านั้น พร้อมทำให้ `canCreate` และเอกสารสอดคล้องกัน ส่วนรายละเอียดวิธีพัฒนาให้ backend ตัดสินใจ
- การเปลี่ยนตัวเลือกหัวข้อและหน้าตา dialog ไม่เปลี่ยนรหัสหัวข้อหรือโครงสร้างข้อมูลที่ส่ง
- การปรับล่าสุดผ่านการตรวจ lint และมี automated tests สำหรับตัวเรียก API การโหลดโรงงานครบทุกหน้า ตัวเลือกหัวข้อจาก JSON และข้อจำกัดการเปิดเรื่องฝั่ง frontend
- ยังไม่ได้ทดสอบ UI และการทำงานครบขั้นตอนด้วยบัญชีจริง จึงยังไม่ยืนยันผลร่วมกับ backend บน production
