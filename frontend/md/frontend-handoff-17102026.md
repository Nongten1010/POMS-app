# ความต้องการเมนู Chat: การเปิดเรื่องและติดตามปัญหา

เอกสารนี้สรุปความต้องการจาก frontend เพื่อให้ backend เข้าใจจุดประสงค์และเงื่อนไขทางธุรกิจ ก่อนออกแบบการทำงานร่วมกัน ไม่ใช่สัญญา API และไม่กำหนดวิธีพัฒนาทางเทคนิค ปัจจุบันมี Mockup ในหน้า Chat ของ frontend แล้ว โดยใช้ข้อมูลจำลอง ไม่เชื่อม API และไม่บันทึกข้อมูลจริง

## จุดประสงค์

- ปรับเมนู Chat ให้เป็นการเปิดเรื่องหรือ Ticket สำหรับสอบถาม แจ้งปัญหา และติดตามการดำเนินการกับเจ้าหน้าที่
- หนึ่ง Ticket มีหนึ่งประวัติการสนทนา ผูกกับโรงงานและจุดตรวจวัดที่เกี่ยวข้อง เพื่อแบ่งพื้นที่การดูแลของเจ้าหน้าที่
- ใช้หน้าตาการสนทนาแบบแชทเพื่อให้อ่านและตอบได้สะดวก แต่ไม่ใช่บริการแชทสด เจ้าหน้าที่อาจใช้เวลาหลายวันในการตอบ
- หน้ารายการต้องใช้พื้นที่อย่างกระชับ โดยเฉพาะเจ้าหน้าที่ที่ต้องดูแลหลายเรื่อง ไม่แบ่งหน้าจอเป็นรายการด้านซ้ายและบทสนทนาด้านขวาตลอดเวลา

## การเริ่มต้นของผู้ประกอบการ

1. เลือกโรงงานที่ตนมีสิทธิ์เข้าถึง
2. เลือกจุดตรวจวัดในโรงงานนั้น หรือเลือก "ทั้งหมด"
3. เลือกหัวข้อการสนทนา
4. พิมพ์และส่งข้อความแรกเพื่อเปิดการสนทนา

- สร้างรายการเมื่อส่งข้อความแรกสำเร็จ ไม่สร้าง Ticket ว่างจากการเปิดหน้าต่างหรือเลือกข้อมูลเพียงอย่างเดียว
- จุดตรวจวัดต้องเป็นของโรงงานที่เลือก และอยู่ในขอบเขตที่ผู้ใช้มีสิทธิ์เข้าถึง
- "ทั้งหมด" หมายถึงเปิดเรื่องระดับโรงงานโดยไม่ระบุหรือผูกจุดตรวจวัด ไม่ใช่การเลือกจุดตรวจวัดทุกจุด และไม่ต้องติดตามว่าจุดใดมีอยู่ ณ วันเปิดเรื่องหรือถูกเพิ่มภายหลัง
- โรงงานที่ยังไม่มีจุดตรวจวัดสามารถเปิดเรื่องได้โดยเลือก "ทั้งหมด"
- รายการโรงงานที่เลือกได้ต้องครอบคลุมทั้งโรงงานที่เชื่อมต่อแล้วและโรงงานที่เข้าข่ายแต่ยังไม่เชื่อมต่อ โดยยังต้องเป็นโรงงานที่ผู้ใช้มีสิทธิ์เข้าถึง ไม่แสดงทุกโรงงานเพียงเพราะเป็นโรงงานที่เข้าข่าย
- โรงงาน จุดตรวจวัดที่เลือก และหัวข้อ ต้องปรากฏให้ผู้ร่วมสนทนาเข้าใจว่าเรื่องนั้นเกี่ยวข้องกับอะไร
- หัวข้อเป็นตัวเลือกกลุ่มเรื่องตามรายการด้านล่าง ไม่ต้องมีช่อง "ประเภท" แยกซ้ำอีกช่อง รายละเอียดปัญหาให้พิมพ์ในข้อความแรก

### ข้อมูลสำหรับ dialog เปิดการสนทนา

| ช่อง | ข้อมูลที่ต้องมีและเงื่อนไข |
| --- | --- |
| โรงงาน | รายการตามสิทธิ์ พร้อมตัวระบุโรงงาน ชื่อ และเลขทะเบียน เพื่อแยกโรงงานชื่อซ้ำ ครอบคลุมโรงงานที่เข้าข่ายแต่ยังไม่เชื่อมต่อด้วย |
| จุดตรวจวัด | รายการของโรงงานที่เลือก พร้อมตัวระบุ รหัส และชื่อจุดตรวจวัด โดยมี "ทั้งหมด" สำหรับเปิดเรื่องระดับโรงงานเสมอ แม้ไม่มีจุดตรวจวัด |
| หัวข้อ | หัวข้อ 6 กลุ่มตามรายการในเอกสารนี้ พร้อมค่าที่ใช้อ้างอิงตอนส่ง |
| ข้อความแรก | ข้อความที่ผู้ใช้กรอก ต้องไม่ว่างและไม่เป็นช่องว่างล้วน |

- ผู้ใช้ไม่ต้องกรอกเลข Ticket ผู้เปิดเรื่อง ภาค จังหวัด หรือสถานะเอง ระบบกำหนดจากบัญชีและโรงงานที่เลือก
- เมื่อเปลี่ยนโรงงาน ต้องไม่คงจุดตรวจวัดของโรงงานเดิมไว้
- Mockup จำกัดข้อความไว้ 2,000 ตัวอักษรเพื่อทดลองใช้งาน ยังไม่ใช่ข้อกำหนดที่ยืนยันสำหรับระบบจริง

## หัวข้อการสนทนา

| หัวข้อ | ขอบเขตของเรื่อง |
| --- | --- |
| ข้อมูลโรงงานและสิทธิ์การใช้งาน | ข้อมูลโรงงาน จุดตรวจวัด และการเข้าถึงข้อมูล |
| การขอเชื่อมต่อและการส่งข้อมูล | คำขอเชื่อมต่อ เพิ่มพารามิเตอร์ ตั้งค่าอุปกรณ์ และข้อมูลไม่เข้า |
| ผลตรวจวัดและการแจ้งเตือน | ค่าตรวจวัด สถิติ ความครบถ้วนของข้อมูล และการแจ้งเตือน |
| แบบฟอร์มและการยื่นรายงาน | การใช้งานแบบฟอร์มและขั้นตอนการยื่นรายงาน รวม กวภ.01–05 และ BOD/COD Online |
| ข้อมูลในแบบฟอร์ม กฎหมายและประกาศฯ | ข้อสอบถามเกี่ยวกับข้อมูลที่ต้องกรอก ความหมายของรายการในแบบฟอร์ม และข้อกำหนดตามกฎหมายหรือประกาศที่เกี่ยวข้อง |
| อื่นๆ | เรื่องที่ไม่อยู่ในหัวข้อข้างต้น |

เลือกหัวข้อหลักหนึ่งหัวข้อต่อ Ticket ไม่แบ่งหัวข้อย่อยในรอบนี้

## สิทธิ์และพื้นที่รับผิดชอบ

- Ticket ผูกกับโรงงาน ไม่ใช่ห้องส่วนตัวระหว่างผู้เปิดเรื่องกับเจ้าหน้าที่คนเดียว
- ผู้ประกอบการทุกคนที่มีสิทธิ์ในโรงงานนั้นสามารถเห็น อ่าน ตอบ และปิด Ticket ของโรงงานนั้นได้ ไม่จำกัดเฉพาะผู้เปิดเรื่อง
- ผู้ไม่มีสิทธิ์ในโรงงานต้องไม่สามารถเข้าถึง Ticket หรือข้อความของโรงงานนั้น
- เจ้าหน้าที่เห็นและดำเนินการกับ Ticket ตามสิทธิ์และขอบเขตพื้นที่รับผิดชอบของตน ไม่ใช่เห็นทุกโรงงานเพียงเพราะเป็นเจ้าหน้าที่
- ใช้การแบ่งภาคแบบกรมโรงงานสำหรับ D-POMS ไม่ใช้การแบ่งภาคทั่วไป ดูรายการที่ยืนยันใน [การแบ่งพื้นที่รับผิดชอบ](../../docs/backend/api/shared/regional-jurisdictions/README.md)
- พื้นที่ของ Ticket อ้างอิงโรงงาน ผู้ประกอบการไม่เลือกภาคผู้รับเรื่องเอง
- เมื่อมีหลายคนร่วมสนทนา ต้องแยกได้ว่าใครเป็นผู้ส่งข้อความ ใครเปิดเรื่อง และใครปิดเรื่อง
- เอกสารนี้ไม่กำหนดสิทธิ์พิเศษเพิ่มเติมให้ Admin และไม่เปลี่ยนสิทธิ์การเข้าถึงโรงงานของระบบเดิม

## หน้ารายการ

ใช้ DataGrid เป็นหน้ารายการ โดยเฉพาะฝั่งเจ้าหน้าที่ ไม่เปิดบทสนทนาค้างไว้เป็นอีกครึ่งหนึ่งของหน้าจอ

| คอลัมน์ | ข้อมูลที่แสดง |
| --- | --- |
| Ticket No. | เลขอ้างอิงเรื่องรูปแบบ `TK-69-xxxxx` เช่น `TK-69-00018` โดยกติกาการเริ่มเลขใหม่เมื่อเปลี่ยนปียังต้องยืนยัน |
| หัวข้อ | หัวข้อการสนทนาที่เลือก |
| ชื่อโรงงาน | ชื่อโรงงานที่ผูกกับเรื่อง |
| เลขทะเบียนโรงงาน | เลขทะเบียนของโรงงานนั้น |
| ภาค | ภาคของโรงงานตามการแบ่งแบบกรมโรงงาน |
| จังหวัด | จังหวัดของโรงงาน |
| สถานะ | เปิดการสนทนา หรือ ปิดการสนทนา |
| ข้อความล่าสุด | วันและเวลาของข้อความล่าสุด ไม่ใช่วันเวลาเปลี่ยนสถานะ การปิดเรื่องไม่เปลี่ยนค่านี้ |
| จัดการ | เปิด dialog เพื่ออ่าน สนทนา หรือดำเนินการตามสิทธิ์และสถานะ |

- เรียงรายการที่มีข้อความล่าสุดก่อน
- ไม่เพิ่มคอลัมน์ประเภทซ้ำกับหัวข้อ และไม่เพิ่มคอลัมน์ผู้รับผิดชอบในรอบนี้
- รายการที่ปิดแล้วต้องยังเข้าถึงประวัติได้ตามสิทธิ์ ไม่หายไปเพียงเพราะปิดการสนทนา

## หน้าต่างสนทนา

- เปิดเป็น dialog จากรายการ Ticket
- ส่วนบนแสดงเลข Ticket โรงงาน จุดตรวจวัดที่เลือก หัวข้อ และสถานะ
- สนทนาเฉพาะข้อความ ไม่รองรับการแนบภาพหรือไฟล์
- ข้อความที่บัญชีปัจจุบันส่งแสดงด้านขวาเสมอ ทั้งกรณีผู้ประกอบการและเจ้าหน้าที่
- ข้อความจากบัญชีอื่นแสดงด้านซ้าย แม้เป็นผู้ประกอบการหรือเจ้าหน้าที่กลุ่มเดียวกัน
- แสดงชื่อผู้ส่ง บทบาท และวันเวลาประกอบข้อความ เพื่อแยกผู้ร่วมสนทนาหลายคน
- ข้อมูลข้อความต้องแยกตัวตนผู้ส่งแต่ละบัญชีได้ เพื่อเทียบกับบัญชีปัจจุบันในการจัดข้อความซ้ายหรือขวา ไม่อาศัยชื่อหรือบทบาทเพียงอย่างเดียว
- ความกว้างของกล่องข้อความปรับตามเนื้อหาอย่างเหมาะสม ไม่แบ่งพื้นที่ข้อความซ้ายและขวาตายตัวแบบ 50/50
- มีช่องพิมพ์และคำสั่งส่งข้อความเฉพาะเมื่อยังเปิดการสนทนาและผู้ใช้มีสิทธิ์
- แสดงเหตุการณ์เปิดและปิดการสนทนาแยกจากข้อความพูดคุย พร้อมผู้ดำเนินการและวันเวลา

## สถานะและการปิดการสนทนา

มีเพียงสองสถานะ:

**เปิดการสนทนา → ปิดการสนทนา**

- เริ่มต้นที่ "เปิดการสนทนา" หลังส่งข้อความแรกสำเร็จ
- ผู้ประกอบการที่มีสิทธิ์ในโรงงานนั้น หรือเจ้าหน้าที่ที่มีสิทธิ์ดูแล Ticket สามารถปิดการสนทนาได้
- ก่อนปิดต้องมี dialog ยืนยัน เพื่อป้องกันการกดผิด
- บันทึกผู้ปิดและวันเวลาที่ปิดไว้ในประวัติ
- เมื่อปิดแล้วอ่านย้อนหลังได้ แต่ส่งข้อความเพิ่มเติมไม่ได้ ไม่ว่าผู้ใช้เป็นผู้ประกอบการหรือเจ้าหน้าที่
- ไม่เปิด Ticket ที่ปิดแล้วกลับมาใช้งานใหม่ หากต้องการสนทนาต่อหรือแจ้งปัญหาเพิ่มเติมให้เปิด Ticket ใหม่
- ไม่เพิ่มสถานะรอรับเรื่อง กำลังดำเนินการ รอข้อมูล หรือรอยืนยัน
- การปิดหน้าต่าง dialog ไม่เท่ากับการปิดการสนทนา ต้องใช้คำสั่งปิดการสนทนาและยืนยันแยกกัน

## การดูข้อความล่าสุด

- ไม่ต้องแสดงข้อความใหม่แบบทันทีเหมือนแชทสด
- โหลดข้อความล่าสุดเมื่อเปิด dialog และมีคำสั่งให้ผู้ใช้รีเฟรชข้อความเอง
- ไม่รีเฟรชเป็นรอบอัตโนมัติ
- หลังผู้ใช้ส่งข้อความสำเร็จ ให้เห็นข้อความของตนในบทสนทนา
- หากเรื่องถูกปิดโดยผู้มีสิทธิ์คนอื่นระหว่างที่ยังเปิด dialog อยู่ ต้องไม่รับข้อความเพิ่มในเรื่องที่ปิดแล้ว และแจ้งให้ผู้ส่งทราบว่าเรื่องถูกปิดแล้ว

## ขอบเขตที่ยังไม่รวม

- ไม่รวมไฟล์แนบ รูปภาพ การโทร หรือการสนทนาแบบสด
- ไม่รวมการมอบหมายผู้รับผิดชอบรายบุคคล บันทึกภายใน หรือขั้นตอนส่งต่อเรื่อง
- ไม่กำหนดให้รวม ลบ หรือเปลี่ยนเมนู "แจ้งขอความช่วยเหลือ" ในงานนี้
- ไม่เพิ่มอีเมลแจ้งเตือนหรือ Badge ใหม่โดยอัตโนมัติ หากต้องการให้ตกลงขอบเขตเพิ่มเติม
- ไม่สร้างช่องทางยกเว้นให้ผู้ที่ไม่มีสิทธิ์เลือกโรงงานเปิด Ticket โดยกรอกเลขทะเบียนเอง หากต้องรองรับกรณีไม่พบโรงงานในบัญชีให้ตกลงเงื่อนไขแยกก่อน

## สิ่งที่ต้องได้จากการทำงานร่วมกัน

Backend รับผิดชอบตัดสินใจแนวทางพัฒนาให้รองรับเงื่อนไขข้างต้น และแจ้งข้อจำกัดหรือประเด็นที่ต้องยืนยันก่อนเปลี่ยนพฤติกรรม ส่วน frontend มีหน้ารายการและ dialog สนทนาแบบ Mockup แล้ว โดยรอเชื่อมต่อการทำงานจริงภายหลัง

เงื่อนไขสำคัญที่ต้องตรวจร่วมกันคือการเข้าถึงตามโรงงานและพื้นที่ การร่วมสนทนาโดยหลายบัญชีในโรงงานเดียวกัน การจัดวางข้อความตามผู้ส่งปัจจุบัน และการไม่รับข้อความเพิ่มหลังปิดเรื่อง โดยไม่กระทบการทำงานของเมนูอื่น
