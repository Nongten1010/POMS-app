# ส่งต่องานหน้าหลัก: เวลา ข้อมูลย้อนหลัง สถานะ และผลตรวจวัด

เอกสารนี้สรุป requirement ที่ยืนยันร่วมกับ frontend สำหรับหน้าหลัก เพื่อให้ backend ตรวจ implementation ปัจจุบันและปรับ API ที่เกี่ยวข้อง โดยใช้ [สัญญา API หน้าหลัก](../../docs/backend/api/menus/home/README.md) เป็น canonical contract เมื่อ implementation เสร็จ

## สถานะและขอบเขต

- เอกสารนี้เป็น requirement handoff ยังไม่ใช่หลักฐานว่า backend รองรับแล้ว
- Requirement ทุกข้อในเอกสารนี้ใช้เฉพาะเมนูหน้าหลักและ API ที่ Frontend ของหน้าหลักเรียกใช้งานเท่านั้น
- ห้ามเปลี่ยน contract, validation, permission, response หรือพฤติกรรมของ API ที่ไม่เกี่ยวข้องกับหน้าหลัก
- ห้ามทำให้หน้าขอเชื่อมต่อ ข้อมูลพื้นฐาน กวภ. BOD/COD รายงาน หรือเมนูอื่นมีพฤติกรรมเปลี่ยนจากเดิม
- หาก endpoint หรือ calculation กลางถูกใช้ร่วมกับเมนูอื่น Backend ต้องแยก context/ขอบเขตการคำนวณของหน้าหลัก หรือรักษาผลลัพธ์เดิมของ consumer อื่นด้วย regression test
- หากไม่สามารถแก้ requirement ของหน้าหลักโดยไม่กระทบเมนูอื่นได้ ต้องหยุดและสอบถามเจ้าของ requirement ก่อน implementation ห้ามขยายขอบเขตเอง
- ข้อมูลตรวจวัดรายชั่วโมงคำนวณเสร็จจากเครื่องตรวจวัดก่อนส่งเข้า Server
- source row ทุกแถวมี `ctime` และ `utime` และไม่มีการแก้ไขแถวภายหลัง
- `ctime` คือเวลาที่เครื่องตรวจวัดได้ค่ารายชั่วโมง
- `utime` คือเวลาที่ Server ได้รับข้อมูล
- การจัดวันและชั่วโมงใช้เขตเวลา `Asia/Bangkok` ให้เหมือนกันทุก endpoint
- ไม่ต้องเพิ่ม endpoint เพียงเพื่อรองรับ requirement ชุดนี้ หาก endpoint เดิมสามารถคืน contract ที่ต้องใช้ได้

## กฎข้อมูลรายชั่วโมงที่ยืนยันแล้ว

### ชั่วโมงที่แสดงบนหน้าหลัก

หน้าหลักแสดงข้อมูลของชั่วโมงก่อนหน้าตามเวลาปัจจุบัน ไม่แสดงชั่วโมงที่กำลังดำเนินอยู่

ตัวอย่างเมื่อเวลาปัจจุบันคือ `10:30`:

| รายการ | ช่วงเวลา |
| --- | --- |
| ชั่วโมงที่กำลังดำเนินอยู่และยังไม่แสดง | `10:00–10:59` |
| ชั่วโมงล่าสุดที่แสดง | `09:00–09:59` |
| เส้นตายรับข้อมูลของชั่วโมงล่าสุด | `09:59` |

ข้อมูลรายชั่วโมงคำนวณมาจากเครื่องแล้ว หากมีข้อมูลของชั่วโมงที่ต้องแสดง Backend สามารถคืนค่าให้ Frontend แสดงได้ทันที ไม่ต้องรอคำนวณเพิ่มอีกหนึ่งชั่วโมง

กรณีเวลาปัจจุบันอยู่ระหว่าง `00:00–00:59` ชั่วโมงล่าสุดที่แสดงคือ `23:00–23:59` ของวันก่อนหน้า

### การใช้ `ctime` และ `utime`

Backend ต้องจัด row เข้าชั่วโมงด้วย `ctime` และตัดสินความตรงเวลาด้วย `utime` เทียบกับเวลาสิ้นสุดของชั่วโมง `ctime` นั้น

| เงื่อนไข | การจำแนก |
| --- | --- |
| `ctime` อยู่ในชั่วโมงเป้าหมาย และ `utime` ไม่เกินเวลาสิ้นสุดชั่วโมง | ส่งข้อมูลตามกำหนด |
| เมื่อสิ้นสุดชั่วโมงแล้วยังไม่พบ row ของช่วงที่ควรมี | ไม่มีข้อมูลส่งมาตามกำหนด |
| `ctime` อยู่ในชั่วโมงเป้าหมาย แต่ `utime` หลังเวลาสิ้นสุดชั่วโมง | ข้อมูลย้อนหลัง และช่วงนั้นยังถือว่าไม่มีข้อมูลส่งมาตามกำหนด |

ตัวอย่าง:

```text
ctime = 09:00
utime = 10:05
```

row นี้เป็นข้อมูลของชั่วโมง `09:00–09:59` แต่เป็นข้อมูลย้อนหลัง เพราะ Server ได้รับหลัง `09:59` ค่าตรวจวัดยังนำมาแสดงย้อนหลังได้ แต่ห้ามย้อนกลับไปเปลี่ยนผลการส่งข้อมูลของชั่วโมง 09 เป็นส่งตามกำหนด

### Snapshot

ไม่ต้องสร้าง snapshot เพื่อแยกข้อมูลตามกำหนด ข้อมูลย้อนหลัง และไม่มีข้อมูล เนื่องจาก `ctime`/`utime` มีทุก row และ row ไม่มีการแก้ไข Backend สามารถคำนวณผลเดิมซ้ำได้จาก timestamps

หากต้องการสร้างผล ณ เวลาหนึ่งในอดีต ให้จำกัด row เพิ่มด้วย `utime <= asOf` ส่วนรายงานที่มีข้อกำหนดให้ผลที่ประกาศแล้วห้ามเปลี่ยนเป็นคนละกรณีและต้องออกแบบ snapshot แยกต่างหาก

## งาน Backend

### 1. ไม่แสดงจุดที่ได้รับการยกเว้นทั้งหมด

- ตัด measurement point ที่มีสถานะ `ได้รับการยกเว้นทั้งหมด` ออกจากข้อมูลหน้าหลัก
- ใช้กับจุดตรวจวัดทั้ง `CEMS` และ `WPMS`
- ใช้กฎเดียวกันทั้งหน้าแรกของผู้ใช้ที่ Login ผ่าน `GET /api/v1/operator-factory-dashboard` และหน้าแรกของประชาชนผ่าน `GET /api/v1/public/factory-map-points`
- จุดที่ได้รับการยกเว้นทั้งหมดต้องไม่ปรากฏใน `measurementPoints`, รายการจุดตรวจวัด, ผลตรวจวัด และ marker บนแผนที่ของหน้าหลัก
- กรองก่อนคำนวณจำนวนจุด สถานะโรงงาน summary และผลรวมอื่น เพื่อไม่ให้จุดที่ไม่แสดงยังถูกนับอยู่
- Backend ต้องใช้สถานะหรือข้อมูลต้นทางที่ยืนยันการยกเว้นทั้งหมดเป็นตัวตัดสิน Frontend ต้องไม่อนุมานการยกเว้นจาก `parameters: []` เพราะ array ว่างอาจเกิดจากข้อมูลพารามิเตอร์ไม่ครบได้
- Contract ปัจจุบันระบุว่าจุดสถานะนี้ยังแสดงด้วย `parameters: []`; backend ต้องแก้ implementation, OpenAPI และ canonical contract ให้ตรง requirement ใหม่

กรณีโรงงานมีเฉพาะจุดที่ได้รับการยกเว้นทั้งหมดว่าจะคง factory row โดยมี `measurementPoints: []` หรือเอาโรงงานออกทั้ง row ยังต้องยืนยันกับเจ้าของ requirement ก่อน implementation

### 2. เปอร์เซ็นต์ข้อมูลย้อนหลัง

- ใช้ `ctime` ระบุ expected hour และใช้ `utime` เทียบกับเวลาสิ้นสุดของ expected hour
- row ที่มาถึงหลังเส้นตายต้องอยู่ในกลุ่มข้อมูลย้อนหลัง แม้ `ctime` ถูกต้อง
- row ย้อนหลังอาจใช้แสดงค่าตรวจวัดได้ แต่ห้ามนับเป็นข้อมูลส่งตามกำหนด
- ไม่ใช้เวลาที่ query หรือเวลาปัจจุบันแทน `utime`
- Backend ต้องระบุ denominator และระดับการนับของเปอร์เซ็นต์ใน contract ให้ชัดว่าเป็นต่อ point, parameter, ชั่วโมง หรือผลรวมใด โดยรักษาความหมายเดียวกันทุก endpoint ที่แสดงเปอร์เซ็นต์นี้

### 3. Section สรุปผลการตรวจวัด

#### จำนวนวันที่ข้อมูลไม่ถึงร้อยละ 80 ต่อวัน

- เป็นจำนวนวันของช่วงที่ต่ำกว่า 80% แบบต่อเนื่องล่าสุด
- รวมวันสิ้นสุดของปฏิทินที่ผู้ใช้เลือก โดยเริ่มตรวจจากวันนั้นแล้วย้อนกลับทีละวัน
- หยุดเมื่อพบวันแรกที่ข้อมูลถึงอย่างน้อย 80%
- หากวันสิ้นสุดมีข้อมูลถึงอย่างน้อย 80% ผลลัพธ์เป็น `0`
- การตัดสินข้อมูลส่งตามกำหนดต้องใช้กฎ `ctime`/`utime` ในเอกสารนี้

ตัวอย่างวันสิ้นสุดคือ 30 กันยายน และวันที่ 28–30 ต่ำกว่า 80% แต่วันที่ 27 ถึงอย่างน้อย 80% ผลลัพธ์คือ `3 วัน`

#### จำนวนวันเกินมาตรฐาน

- นับจำนวนวันที่เกินมาตรฐานตั้งแต่วันที่ 1 มกราคมของปีที่เลือกจนถึงวันสิ้นสุดของปฏิทินที่เลือก โดยรวมวันต้นและวันสิ้นสุด
- เป็นยอดสะสมในปี ไม่ใช่จำนวนวันต่อเนื่อง
- นับเป็น unique day: หากวันเดียวกันมีอย่างน้อยหนึ่งพารามิเตอร์เกินมาตรฐาน ให้นับวันนั้นเพียงหนึ่งวัน แม้มีหลายพารามิเตอร์หรือเกินหลายครั้ง
- ระดับเฝ้าระวังไม่นับเป็นวันเกินมาตรฐาน
- ใช้เกณฑ์มาตรฐานและ precedence เดิมของระบบสำหรับตัดสินว่าแต่ละวันเกินมาตรฐานหรือไม่

#### การส่งข้อมูลวันนี้

- ปัจจุบันเวลาและค่าที่แสดงในตารางสถิติข้อมูลถูกต้องแล้ว ขอบเขตการแก้ไขส่วนนี้คือสูตรเปอร์เซ็นต์ “การส่งข้อมูลวันนี้” และ calculation กลางที่ API ปฏิทินใช้ร่วมกัน ห้ามเปลี่ยน source row หรือช่วงเวลาของตารางที่ถูกต้องอยู่แล้วโดยไม่มีเหตุผลจาก contract
- ผลลัพธ์ที่แสดงเป็นเปอร์เซ็นต์เท่านั้น ไม่แสดงจำนวนชั่วโมงหรือจำนวนรายการประกอบ
- วันปัจจุบันใช้เกณฑ์เวลาปัจจุบันลบ 1 ชั่วโมง โดยหมายถึงชั่วโมงปฏิทินก่อนหน้าแบบเต็มชั่วโมง ไม่ใช่ rolling window ย้อนหลัง 60 นาที
- แสดงเฉพาะชั่วโมงที่จบแล้ว ตั้งแต่ต้นวันตามกติกาของระบบถึงเวลาสิ้นสุดของชั่วโมงก่อนหน้า
- ตัวอย่างเวลา `10:30` ให้คำนวณตั้งแต่ต้นวันถึง `09:59`; ชั่วโมงล่าสุดที่รวมคือ `09:00–09:59` และไม่รวมข้อมูล `10:00–10:59`
- ใช้ cutoff เดียวกันกับการเลือกข้อมูลล่าสุดบนหน้าหลัก และการคำนวณวันปัจจุบันใน API ปฏิทิน
- ข้อมูลที่ `utime` เกินเวลาสิ้นสุดของชั่วโมงไม่นับเป็นส่งตามกำหนด
- เมื่อเลือกวันย้อนหลัง ให้คำนวณจาก `ctime`/`utime` ตามกฎเดียวกัน ไม่อ่านสถานะจากค่าที่ถูกเขียนทับภายหลัง
- Backend ต้องคืนเปอร์เซ็นต์จากจำนวนข้อมูลรายชั่วโมงที่ส่งตามกำหนดเทียบกับจำนวนข้อมูลรายชั่วโมงที่คาดว่าจะได้รับในช่วงที่นำมาคำนวณ และบันทึกระดับการ aggregate/denominator ที่ใช้อยู่จริงไว้ใน canonical contract

ปัญหาที่พบในระบบปัจจุบันคือ ตารางสถิติแสดงเวลาและค่าถูกต้อง แต่ “การส่งข้อมูลวันนี้” แสดง `95%` ทั้งที่ทุกชั่วโมงที่จบแล้วส่งข้อมูลครบ สาเหตุที่ต้องตรวจคือ denominator อาจรวมชั่วโมงปัจจุบันที่ยังไม่จบเป็น expected hour และนับชั่วโมงนั้นเป็นข้อมูลขาด

กฎที่ต้องได้หลังแก้:

- denominator มีเฉพาะชั่วโมงที่จบแล้วจนถึงชั่วโมงปฏิทินก่อนหน้า
- ชั่วโมงปัจจุบันต้องไม่อยู่ทั้ง numerator และ denominator
- หากทุก expected hour ที่จบแล้วมีข้อมูลส่งตามกำหนด ผลต้องเป็น `100%` แม้ยังไม่มีข้อมูลของชั่วโมงปัจจุบัน
- หากมี expected hour ที่จบแล้วขาดข้อมูล จึงค่อยลดเปอร์เซ็นต์ตามจำนวนที่ขาดจริง

#### ใช้เกณฑ์เดียวกับ API ปฏิทิน

Backend ต้องใช้ calculation กลางชุดเดียวกันระหว่างหน้าหลัก ตารางสถิติ และ API ปฏิทิน โดย endpoint หลักที่ตรวจพบว่าต้องแก้คือ:

- `GET /api/v1/connected-measurement-points/:stationId/calendar-status`
- `GET /api/v1/connected-measurement-points/:stationId/measurement-statistics`

ตัวอย่าง production ที่ใช้ยืนยันปัญหา:

- `GET /api/v1/connected-measurement-points/S1128/calendar-status?month=2026-09`
- `GET /api/v1/connected-measurement-points/S1128/measurement-statistics?date=2026-09-23`

`GET /api/v1/connected-measurement-points/:stationId/calendar-status/details` ต้องตรวจ regression และใช้ผลรายวันชุดเดียวกัน หาก endpoint นี้อ่าน calculation หรือ summary เดียวกับ `calendar-status`

กฎที่ต้องใช้ร่วมกันประกอบด้วย:

- การเลือก expected hour และการตัดชั่วโมงปัจจุบันออก
- cutoff ของวันปัจจุบันต้องสิ้นสุดที่นาที `59` ของชั่วโมงปฏิทินก่อนหน้า เช่น เวลา `10:30` ใช้ข้อมูลถึง `09:59`
- การใช้ `ctime` จัดวัน/ชั่วโมง และ `utime` แยกส่งตามกำหนดกับข้อมูลย้อนหลัง
- denominator และสูตรเปอร์เซ็นต์การส่งข้อมูล/ความครบถ้วน
- เกณฑ์ต่ำกว่า 80% และการนับช่วงต่อเนื่องล่าสุด
- เกณฑ์มาตรฐานของแต่ละพารามิเตอร์ รวม source status ที่อนุญาตให้นำค่าไปเทียบ
- การตัดสิน `normal`, `warning`, `exceeded` และ `insufficient`
- การนับ unique day ที่เกินมาตรฐาน
- เขตเวลา `Asia/Bangkok` และขอบเขตวันตามปฏิทิน

เมื่อใช้ station, parameter, วันที่ และข้อมูล source ชุดเดียวกัน ผลจากหน้าหลัก ตารางสถิติ และปฏิทินต้องตรงกันทั้งเปอร์เซ็นต์และสถานะมาตรฐาน Frontend ต้องใช้ค่าที่ Backend คืนและไม่คำนวณเกณฑ์อีกชุดหนึ่งเอง

ค่าที่ API ปฏิทินคืนใน `calendar.days[]`, `monthlySummary[]` และรายละเอียดจาก `calendar-status/details` ต้องมาจาก calculation เดียวกัน เพื่อไม่ให้ยอดสรุปกับรายการวันที่คลิกดูไม่ตรงกัน

### 4. สีและสถานะของข้อมูลย้อนหลัง

Backend ต้องคืนข้อมูลเพียงพอให้ Frontend แยกอย่างน้อยสามกรณี:

1. ค่าปกติที่ส่งตามกำหนด
2. ค่าที่ส่งย้อนหลัง
3. ค่าที่อยู่ระดับเฝ้าระวังหรือเกินมาตรฐาน

ลำดับความสำคัญในการแสดงสีคือ:

1. สีเกินมาตรฐานหรือเฝ้าระวังตามเกณฑ์
2. สีน้ำเงินสำหรับข้อมูลย้อนหลังที่ไม่เข้าเกณฑ์ข้อ 1
3. สีปกติของข้อมูลทั่วไป

Backend ควรคืนสถานะเชิงความหมาย ไม่ผูก contract กับรหัสสีของ Frontend และต้องประเมินสถานะเกณฑ์กับค่าที่ส่งย้อนหลังด้วย

ใช้ status `lateData` สำหรับค่าที่เดิมประเมินได้เป็น `normal` แต่ `utime` เกินเวลาสิ้นสุดของชั่วโมงตาม `ctime` คำว่า `lateData` หมายถึงข้อมูลมาถึง Server หลังเวลาที่กำหนดโดยตรง จึงชัดกว่า `old` และไม่สับสนกับข้อมูลของวันที่ย้อนหลังซึ่งอาจส่งมาตามกำหนด

ไม่ต้องเพิ่ม boolean flag แยกสำหรับกรณีนี้ Frontend อ่าน status ที่ Backend สรุปแล้วเพื่อเลือกการแสดงผล

ตัวอย่างผลที่ต้องสื่อได้:

| สถานะก่อนพิจารณาเวลาส่ง | เงื่อนไขเวลา | Status ที่ Backend คืน | ผลที่ Frontend แสดง |
| --- | --- | --- | --- |
| `normal` | ส่งตามกำหนด | `normal` | สีปกติ |
| `normal` | ส่งย้อนหลัง | `lateData` | สีน้ำเงิน |
| `warning` | ส่งตามกำหนดหรือย้อนหลัง | `warning` | สีเฝ้าระวัง |
| `exceeded` | ส่งตามกำหนดหรือย้อนหลัง | `exceeded` | สีเกินมาตรฐาน |

ลำดับการสรุป status คือ `exceeded` > `warning` > `lateData` > `normal` ส่วน `insufficient`, `noData` และ `invalid` ให้คงกฎเดิมของระบบ และ Backend ต้องบันทึก `lateData` เพิ่มใน response schema, OpenAPI และ canonical contract ของ endpoint ที่ได้รับผลกระทบ

### 5. ค้นหาขั้นสูงด้วยนิคมอุตสาหกรรม

- Frontend ปัจจุบันกรองรายการที่ได้รับจาก `GET /api/v1/operator-factory-dashboard` ภายใน browser และไม่ได้ส่ง query นิคมกลับไปค้นหาที่ Backend
- Frontend แก้ให้ใช้ `industrialAreaType` เป็นหลัก โดย `INDUSTRIAL_ESTATE` คือในนิคม และ `OUTSIDE_INDUSTRIAL_ESTATE` คือนอกนิคม พร้อม fallback จาก `industrialEstateCode` หรือ `industrialEstateName` เมื่อ response รุ่นเดิมไม่มี `industrialAreaType`
- ปัญหาข้อมูลที่ตรวจพบคือบางโรงงานอาจมี `industrialEstateName` แต่ `industrialEstateCode` เป็น `null` แม้ Backend ระบุ `industrialAreaType: "INDUSTRIAL_ESTATE"`; Backend ต้องตรวจสาเหตุที่ชื่อจากข้อมูลโรงงานจับคู่กับ master `industrial_estates` แล้วไม่ได้รหัส เช่น ความต่างของชื่อหรือรูปแบบข้อมูล
- `GET /api/v1/operator-factory-dashboard` และ `GET /api/v1/public/factory-map-points` ต้องคืน `industrialAreaType`, `industrialEstateCode` และ `industrialEstateName` ให้สอดคล้องกัน โดยโรงงานในนิคมควรมีทั้งรหัสและชื่อเมื่อจับคู่ master ได้
- ห้ามจำแนกโรงงานเป็นนอกนิคมเพียงเพราะ `industrialEstateCode` เป็น `null` หากยังมีชื่อหรือข้อมูลต้นทางที่ยืนยันว่าอยู่ในนิคม
- เพิ่ม regression test สำหรับโรงงานในนิคมที่มี code/name ครบ โรงงานในนิคมที่ยังจับคู่ master ไม่ได้ โรงงานนอกนิคม และผู้ใช้ scope `IN_ESTATE`

### 6. สถานะแสดง/ซ่อนต้องมีผลกับหน้าหลัก

Requirement นี้ใช้เฉพาะ API ที่หน้าแรกเรียกใช้งาน ไม่รวม API ของเมนูข้อมูลพื้นฐานหรือ API จัดการสถานะแสดง/ซ่อน ผู้มีสิทธิ์จัดการจึงยังต้องเห็นรายการที่ซ่อนในเมนูจัดการและสามารถเปลี่ยนกลับเป็น `แสดง` ได้

Backend ต้องใช้ effective visibility แบบลำดับชั้นดังนี้:

1. โรงงานมีสถานะ `ซ่อน`: ไม่คืน factory row และไม่คืนจุดตรวจวัด พารามิเตอร์ ผลตรวจวัด หรือ marker ใดของโรงงานนั้น
2. โรงงานแสดง แต่จุดตรวจวัดมีสถานะ `ซ่อน`: ไม่คืน measurement point นั้น รวมถึงพารามิเตอร์และผลตรวจวัดทั้งหมดของจุดนั้น
3. โรงงานและจุดตรวจวัดแสดง แต่พารามิเตอร์มีสถานะ `ซ่อน`: ไม่คืนพารามิเตอร์นั้นและไม่คืนค่าตรวจวัดของพารามิเตอร์นั้น ส่วนพารามิเตอร์อื่นที่แสดงยังใช้งานตามปกติ

รายการลูกที่มีสถานะ `แสดง` ไม่สามารถลบล้างสถานะ `ซ่อน` ของ parent ได้ เช่น จุดตรวจวัดที่แสดงภายใต้โรงงานที่ซ่อนยังต้องถูกตัดออกจากหน้าแรกทั้งหมด

การกรองต้องเกิดก่อนสร้าง response และก่อนการคำนวณทุกชนิดของหน้าแรก ได้แก่:

- จำนวนโรงงาน จำนวนจุดตรวจวัด และจำนวนพารามิเตอร์
- factory summary, point summary และสถานะรวมของโรงงาน/จุดตรวจวัด
- latest-hour flag, ข้อมูลชั่วโมงล่าสุด และข้อมูลใน marker/popup แผนที่
- expected data, numerator, denominator และเปอร์เซ็นต์การส่งข้อมูล
- จำนวนวันที่ข้อมูลต่ำกว่าร้อยละ 80 และช่วงต่อเนื่องล่าสุด
- ระดับ `normal`, `lateData`, `warning`, `exceeded`, `insufficient` และจำนวนวันเกินมาตรฐาน
- ข้อมูลและ summary ของปฏิทิน ตารางสถิติ และรายละเอียดวันที่

โรงงาน จุดตรวจวัด และพารามิเตอร์ที่มี effective visibility เป็น `ซ่อน` ให้ถือว่าไม่ได้ถูกใช้งานสำหรับหน้าแรก จึงต้องไม่ถูกส่งออกและต้องไม่มีผลต่อการคำนวณ แม้ฐานข้อมูลตรวจวัดยังมี row ของรายการนั้นอยู่

กฎนี้ต้องใช้กับ API หน้าแรกทั้งหมดต่อไปนี้และ calculation กลางที่ endpoint เหล่านี้เรียกใช้:

- `GET /api/v1/operator-factory-dashboard`
- `GET /api/v1/public/factory-map-points`
- `GET /api/v1/connected-measurement-points/:stationId/calendar-status`
- `GET /api/v1/connected-measurement-points/:stationId/measurement-statistics`
- `GET /api/v1/connected-measurement-points/:stationId/calendar-status/details`

หากเรียก endpoint รายจุดด้วย `stationId` ของจุดที่ซ่อน หรือจุดที่อยู่ภายใต้โรงงานที่ซ่อน API ต้องไม่คืนข้อมูลตรวจวัดของจุดนั้น เมื่อเปลี่ยนสถานะแล้ว request รอบถัดไปต้องสะท้อนผลทันทีโดยไม่ต้องแก้หรือลบข้อมูลตรวจวัดเดิม

### 7. ผลตรวจวัดเมื่อคลิกไอคอนแผนที่

- Public map response ต้องมีผลตรวจวัดของแต่ละจุดเพียงพอให้ Frontend แสดงเมื่อคลิก marker
- ใช้ข้อมูลของชั่วโมงล่าสุดตามกฎชั่วโมงก่อนหน้าในเอกสารนี้
- คงชื่อพารามิเตอร์พร้อมหน่วย ค่า/สถานะ วันเวลา จุดตรวจวัด และระบบ CEMS/WPMS ตาม contract เดิม
- ใช้กฎยกเว้นทั้งหมด visibility ข้อมูลย้อนหลัง และสีตามเกณฑ์ชุดเดียวกับตาราง เพื่อไม่ให้ popup กับตารางขัดกัน
- หาก `GET /api/v1/public/factory-map-points` คืน fields เหล่านี้ครบแล้ว ไม่ต้องเพิ่ม endpoint ให้แก้เฉพาะการเลือกข้อมูลและ contract ที่ไม่ตรง requirement

## งาน Frontend ที่พึ่งพา Backend

- ใช้สถานะย้อนหลังและระดับเกณฑ์จาก API เพื่อเลือกสี โดยเกณฑ์เฝ้าระวัง/เกินมาตรฐานมี precedence เหนือสีน้ำเงิน
- ใช้ `industrialAreaType` จาก API เป็นหลักในการกรองพื้นที่ประกอบกิจการ และใช้ code/name เป็น fallback เฉพาะ response รุ่นเดิม
- หลังเปลี่ยนสถานะแสดง/ซ่อน ให้ reload ข้อมูลหน้าหลักและนำรายการที่ซ่อนออกจากตาราง/แผนที่
- แสดงผลตรวจวัดจาก public map response ใน popup เมื่อคลิก marker

งาน Frontend ที่ไม่ต้องรอ Backend ได้แก่การซ่อนปุ่ม `>` สำหรับบัญชี `public_user` ส่วนคำว่า `ยอดเข้าดู*` ยังไม่มีรายละเอียดว่าต้องแก้ข้อความ รูปแบบ หรือค่าใด จึงยังไม่อยู่ในเกณฑ์ตรวจรับ

## จุดที่ต้องยืนยันก่อน Backend ปิดงาน

1. โรงงานที่เหลือเฉพาะจุดสถานะ `ได้รับการยกเว้นทั้งหมด` ต้องคง factory row หรือเอาออกจากหน้าหลักทั้งหมด
2. เปอร์เซ็นต์ข้อมูลย้อนหลังใช้ denominator ระดับใด และเมื่อพารามิเตอร์ของชั่วโมงเดียวกันมาถึงไม่พร้อมกันต้องสรุปอย่างไร
3. Popup แผนที่ต้องแสดงทุกพารามิเตอร์หรือเฉพาะพารามิเตอร์ที่มีค่าในชั่วโมงล่าสุด และต้องแสดงประวัติย้อนหลังหรือไม่
4. จุดเริ่มต้นของ “การส่งข้อมูลวันนี้” ที่ระบุว่า `00:01` ต้องจับคู่กับ hourly row เวลา `00:00` อย่างไร เพื่อไม่ให้ชั่วโมงแรกหายจาก denominator

## API และเอกสารที่ได้รับผลกระทบ

อย่างน้อยต้องตรวจ endpoint ต่อไปนี้:

- `GET /api/v1/operator-factory-dashboard`
- `GET /api/v1/public/factory-map-points`
- `GET /api/v1/connected-measurement-points/:stationId/calendar-status`
- `GET /api/v1/connected-measurement-points/:stationId/measurement-statistics`
- `GET /api/v1/connected-measurement-points/:stationId/calendar-status/details`
- API อื่นที่เรียก calculation กลางเดียวกันไม่อยู่ในขอบเขตแก้ไข ให้ตรวจ regression ว่าผลลัพธ์เดิมของเมนูอื่นไม่เปลี่ยน หากจำเป็นต้องเปลี่ยนต้องสอบถามก่อน
- ฟิลด์ข้อมูลนิคมใน `operator-factory-dashboard` และ `public/factory-map-points`

Client-visible response, query, status หรือพฤติกรรมที่เปลี่ยนต้องอัปเดตพร้อมกันใน:

- runtime OpenAPI ภายใต้ `backend/src/modules/api-docs/`
- [Canonical API หน้าหลัก](../../docs/backend/api/menus/home/README.md)
- [Canonical API สถิติข้อมูล](../../docs/backend/api/menus/statistics/README.md) หรือ shared measurement contract ที่ endpoint ใช้จริง
- `docs/backend/api/CHANGELOG.md` หากเป็น breaking change

รายการเอกสารข้างต้นมีไว้เพื่ออัปเดต contract ของ endpoint หน้าแรกเท่านั้น ไม่ใช่อนุญาตให้เปลี่ยน endpoint หรือเมนูอื่นที่อยู่ในเอกสาร canonical เดียวกัน

[Calendar Current-Day Completeness Workflow](../../workflows/calendar-current-day-completeness.md) ปัจจุบันนับชั่วโมงที่กำลังดำเนินอยู่เป็น expected bucket ซึ่งขัดกับ requirement ใหม่นี้ Backend ต้องแก้ workflow, implementation และ tests ให้ใช้ชั่วโมงก่อนหน้าเมื่อเริ่มงาน

- [ ] เปอร์เซ็นต์ “การส่งข้อมูลวันนี้” เวลา `10:30` คำนวณตั้งแต่ต้นวันถึง `09:59` ด้วย expected hours ชุดเดียวกับ API ปฏิทินวันปัจจุบัน
- [ ] กรณีทุกชั่วโมงที่จบแล้วส่งครบ แต่ชั่วโมงปัจจุบันยังไม่มีข้อมูล ต้องคืน `100%` ไม่ใช่ `95%` หรือเปอร์เซ็นต์ที่ถูกลดจากชั่วโมงปัจจุบัน
- [ ] การแก้เปอร์เซ็นต์ไม่เปลี่ยนเวลาและค่าที่ตารางสถิติข้อมูลแสดงถูกต้องอยู่แล้ว

- [ ] row ชั่วโมง 09 ที่ `utime > 09:59` แสดงเป็นข้อมูลย้อนหลัง แต่ชั่วโมงนั้นไม่นับเป็นส่งตามกำหนด
- [ ] เมื่อข้อมูลย้อนหลังมาถึงภายหลัง เปอร์เซ็นต์ส่งตามกำหนดไม่เพิ่มย้อนหลัง
- [ ] วันสิ้นสุดต่ำกว่า 80% หลายวันติดกันนับย้อนหลังจนพบวันแรกที่ถึง 80%; วันสิ้นสุดถึง 80% คืน `0`
