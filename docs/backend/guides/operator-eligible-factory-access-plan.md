# แผนผูกผู้ประกอบการกับโรงงานที่ยังไม่แจ้งประกอบและตรวจสถานะ Fac60k

[กลับไปคู่มือ Backend](./README.md) · [การยืนยันตัวตน](../api/shared/authentication/README.md) · [โรงงานที่เข้าข่าย](../api/menus/eligible-factories/README.md)

> สถานะ: แผนสำหรับพัฒนาต่อ ยังไม่ใช่พฤติกรรมที่เปิดใช้งานหรือ API contract ใหม่ งานจัดทำเอกสารนี้ไม่แก้โค้ด ไม่สร้างตาราง ไม่ตั้งงานประจำวัน และไม่เปลี่ยนสิทธิ์หรือข้อมูลจริง

## เป้าหมายและขอบเขต

รองรับผู้ประกอบการที่ยืนยันตัวตนกับ i-industry สำเร็จ แต่ไม่ได้รับรายชื่อโรงงานที่ยังไม่แจ้งประกอบ โดยให้เจ้าหน้าที่ผูกบัญชีกับโรงงานใน `eligible_factories` และนำโรงงานที่ผูกไว้มารวมกับรายชื่อเดิมหลัง login พร้อมตรวจสถานะจาก Fac60k ทุกวัน

ขอบเขตการพัฒนาตามแผนคือ backend และเอกสารที่เกี่ยวข้อง การเปลี่ยน frontend ต้องเป็นงานที่ผู้ใช้สั่งแยกอย่างชัดเจน เอกสารนี้ไม่กำหนด endpoint หรือ request/response ใหม่แทน canonical contract ที่มีอยู่

## แหล่งข้อมูลและความรับผิดชอบ

| ข้อมูล | หน้าที่ในแผน |
| --- | --- |
| i-industry | ยืนยันตัวตนและให้ข้อมูลความสัมพันธ์ผู้ประกอบการ/นิติบุคคล/โรงงานตามระบบเดิม |
| Fac60k | ทะเบียนโรงงานต้นทางสำหรับอ่านสถานะประกอบกิจการ ไม่เขียนข้อมูลจาก POMS กลับไป |
| `eligible_factories` | รายการโรงงานที่เจ้าหน้าที่เลือกเป็นโรงงานเข้าข่าย และโรงงานเป้าหมายของการผูกเพิ่มเติม |
| `factories` | ข้อมูล master/identity และสิทธิ์เดิม ไม่ใช่ชุดโรงงานที่เชื่อมต่อ POMS สำเร็จ |
| active rows ใน `cems_wpms_connected_measurement_points` | ข้อมูลโรงงานในระบบ POMS หลังเชื่อมต่อสำเร็จ ไม่สร้างหรือยกเลิกจากการผูกผู้ประกอบการ |
| รายการผูกเพิ่มเติม | ความสัมพันธ์ที่เจ้าหน้าที่อนุมัติให้ผู้ใช้เข้าถึงโรงงานเข้าข่ายเฉพาะราย ในช่วงที่โรงงานยังไม่แจ้งประกอบ |

การแจ้งประกอบ การเป็นโรงงานเข้าข่าย การได้รับสิทธิ์ และการเชื่อมต่อสำเร็จ เป็นคนละเรื่องกัน การผูกสิทธิ์ไม่เปลี่ยนสถานะโรงงาน ไม่เพิ่มโรงงานเข้าข่ายอัตโนมัติ และไม่ทำให้คำขอเชื่อมต่อผ่านการอนุมัติ

## พื้นฐานที่มีอยู่และจุดที่ต้องพัฒนา

| ส่วน | พื้นฐานปัจจุบัน | งานตามแผน |
| --- | --- | --- |
| Login ผู้ประกอบการ | ถ้า provider ส่ง `juristics` ว่าง จะเข้าสู่ citizen flow | ตรวจสิทธิ์ผูกเพิ่มเติมก่อนตัดสิน persona เมื่อผู้ใช้เลือกเข้าแบบ operator |
| สิทธิ์รายโรงงาน | มี `user_factory_access` ที่อ้างถึง `factories` และ `user_juristics` | รองรับสิทธิ์ที่ผูกกับ `eligible_factories` โดยตรงและรวมกับการตรวจสิทธิ์เดิม |
| รายชื่อหลัง login | สร้างรายชื่อสิทธิ์เดิมผ่าน factory master | รวมโรงงานที่ผูกเพิ่มโดยไม่สร้างโรงงานหรือ identity จำลอง |
| การเติมข้อมูลจากต้นทาง | มี read-only hydration ของข้อมูลบางส่วน | เพิ่มงานตรวจและบันทึกการเปลี่ยนสถานะรายวัน ไม่ถือว่า hydration คือการ sync สถานะแล้ว |
| การค้นหา candidate | รับ `FFLAG` เฉพาะ `0`, `1`, `3` | งาน sync ต้องอ่านได้ทุกสถานะ รวม `2` โดยแยกจากตัวกรอง candidate |

อ้างอิง implementation ที่เกี่ยวข้องในหัวข้อท้ายเอกสาร พื้นฐานเหล่านี้ไม่ใช่หลักฐานว่า flow ใหม่ทำงานแล้ว

## 1. การผูกผู้ประกอบการกับโรงงานเข้าข่าย

1. เจ้าหน้าที่ที่ได้รับสิทธิ์จัดการรายการผูก เลือกบัญชีผู้ประกอบการที่เคยยืนยันตัวตนผ่าน i-industry แล้ว
2. เลือกโรงงานเข้าข่ายที่ยังไม่ถูกลบ และตรวจสถานะจาก Fac60k ให้ใหม่พอตามนโยบายที่กำหนด
3. อนุญาตให้ผูกเฉพาะสถานะ `ยังไม่แจ้งประกอบ` (`FFLAG = 0`) เท่านั้น หากยืนยันสถานะไม่ได้ ยังไม่สร้างสิทธิ์ใหม่
4. บันทึกผู้ให้สิทธิ์ วันเวลา เหตุผล และข้อมูลอ้างอิงหลักฐาน พร้อมป้องกันรายการผูกที่ยังมีผลซ้ำกัน
5. รองรับผู้ประกอบการหนึ่งคนหลายโรงงาน และโรงงานหนึ่งแห่งหลายผู้ประกอบการ โดยแต่ละคู่ต้องได้รับอนุมัติแยกกัน

ผูกกับตัวตนบัญชี POMS ที่เชื่อมกับ provider identity ที่ตรวจสอบแล้ว ไม่จับคู่ด้วยชื่อบุคคล อีเมล หรือเลขที่ผู้เรียกกรอกเองโดยไม่มีการยืนยัน และไม่เพิ่มรายชื่อผู้ใช้/โรงงานแบบ hardcode

ข้อเสนอการจัดเก็บคือ `user_eligible_factory_access` ซึ่งอ้างถึง `users.id` และ `eligible_factories.id` โดยตรง ชื่อนี้เป็นข้อเสนอสำหรับออกแบบ schema ไม่ใช่ตารางที่สร้างแล้ว ข้อมูลขั้นต่ำประกอบด้วยผู้ใช้ โรงงาน ผู้ให้สิทธิ์ เวลาให้สิทธิ์ เหตุผล ข้อมูลอ้างอิงหลักฐาน และข้อมูลผู้เพิกถอน/เวลา/เหตุผลเมื่อสิทธิ์สิ้นสุด

การผูกโรงงานแห่งหนึ่งต้องไม่ขยายสิทธิ์ไปทุกโรงงานของนิติบุคคลเดียวกัน การเพิกถอนต้องมีผลต่อการเรียกใช้งานครั้งถัดไปและเก็บประวัติไว้

## 2. การเพิ่มรายชื่อโรงงานหลัง login

```text
ผู้ใช้เลือกเข้าแบบ operator
    → i-industry ยืนยันตัวตนสำเร็จ
    → หา/สร้างบัญชีจาก provider identity ตามกติกาเดิม
    → รับและประมวลผลข้อมูลโรงงานตาม flow เดิม
    → ค้นหารายการผูกเพิ่มเติมที่ยังมีผลของผู้ใช้
    → ตรวจสถานะโรงงานที่ผูกและความสดของข้อมูล
    → รวมรายชื่อและตัดโรงงานซ้ำ
    → คืนรายชื่อและสิทธิ์ให้ผู้ใช้เลือกขอเชื่อมต่อ
```

| เงื่อนไข | ผลที่ต้องรองรับ |
| --- | --- |
| i-industry ส่ง A, B และมีรายการผูก C ที่ยังมีผล | ได้ A, B, C |
| i-industry ไม่ส่งโรงงาน แต่มีรายการผูก C ที่ยังมีผล | เข้าแบบ operator และได้ C |
| i-industry ไม่ส่งนิติบุคคล แต่ยืนยันตัวตนสำเร็จและมีรายการผูก C ที่ยังมีผล | ไม่ตกเป็น citizen เพียงเพราะ `juristics` ว่าง; เข้าแบบ operator และได้ C |
| ไม่มีข้อมูลนิติบุคคลจาก provider และไม่มีรายการผูกที่ใช้ได้ | ใช้ fallback ตาม contract เดิม |
| ผู้ใช้เลือกเข้าแบบ citizen | คง citizen persona ตามเดิม ไม่เพิ่มสิทธิ์ operator อัตโนมัติ |
| i-industry ยืนยันตัวตนไม่สำเร็จ | ไม่ใช้รายการผูกเป็นทางข้ามการยืนยันตัวตน |

ตัดซ้ำด้วย identity โรงงานที่ตรวจสอบแล้ว โดยใช้ความสัมพันธ์ของรายการเข้าข่ายกับ FID/เลขทะเบียนใหม่ตามกติกาปัจจุบัน ไม่เทียบจากชื่อและไม่ใช้เลขทะเบียนเดิมแทนเลขใหม่ หากจับคู่กำกวมให้แยกตรวจสอบ ไม่รวมสิทธิ์โดยเดา

ให้ login, `/auth/me`, รายการโรงงาน และการอ่าน/สร้าง/แก้ไขคำขอ ใช้กติกาสิทธิ์เดียวกัน พร้อมตรวจ permission ของ action ตามปกติ รายชื่อที่ส่งกลับ client ไม่ใช่หลักฐานสิทธิ์แทนการตรวจที่ backend

ตอนออกแบบ response ต้องรักษาความหมาย `ownedFactoryIds` และตัวระบุโรงงานเดิม ห้ามนำ `eligible_factories.id` ไปใส่แทน FID หรือสร้าง FID/นิติบุคคลจำลอง หาก contract เดิมแทนโรงงานที่ผูกเพิ่มไม่ได้ ต้องกำหนดการขยาย contract ให้ชัดและอัปเดต OpenAPI กับ canonical docs ในงาน implementation

## 3. เมื่อสถานะโรงงานเปลี่ยน

รายการผูกเพิ่มเติมมีผลเมื่อรายการยังไม่ถูกเพิกถอน โรงงานยังอยู่ในรายการเข้าข่าย และสถานะต้นทางที่ยืนยันได้ยังเป็น `FFLAG = 0` ต้องตรวจเงื่อนไขนี้ทั้งตอน login และตอนใช้สิทธิ์ ไม่อาศัยเฉพาะสถานะวันที่ผูกหรือข้อมูลที่ฝังไว้ใน token

| สถานะจาก Fac60k | สิทธิ์ผูกเพิ่มเติม | การดำเนินการ |
| --- | --- | --- |
| `0` — `ยังไม่แจ้งประกอบ` | ใช้ได้หากเงื่อนไขอื่นครบ | รวมในรายการโรงงานของผู้ใช้ |
| `1` — `แจ้งประกอบแล้ว` และมีสิทธิ์จาก i-industry | หยุดใช้สิทธิ์ผูกพิเศษ | ใช้สิทธิ์เดิมจาก i-industry แสดงโรงงานเพียงรายการเดียว |
| `1` — `แจ้งประกอบแล้ว` แต่ไม่มีสิทธิ์จาก i-industry | หยุดใช้สิทธิ์ผูกพิเศษ | ไม่ให้สิทธิ์ต่อโดยอัตโนมัติ ส่งให้เจ้าหน้าที่ตรวจสอบ |
| `2` — `จำหน่ายทะเบียน` | ใช้สิทธิ์ผูกพิเศษไม่ได้ | บันทึกการเปลี่ยนสถานะและให้เจ้าหน้าที่ตรวจผลกระทบ |
| `3` — `หยุดชั่วคราว` | ใช้สิทธิ์ผูกพิเศษไม่ได้ | บันทึกการเปลี่ยนสถานะ; สิทธิ์จากแหล่งอื่นใช้กติกาเดิม |
| ไม่พบแถวต้นทาง / สถานะไม่รู้จัก / อ่านต้นทางไม่ได้ | ยังสรุปการเปลี่ยนสถานะไม่ได้ | เก็บสถานะที่ยืนยันล่าสุดและบันทึกปัญหา ไม่เดาว่าเป็น `0` หรือ `2` |

เมื่อยืนยันได้ว่าสถานะออกจาก `0` ให้บันทึกเหตุที่รายการผูกหยุดมีผลและเก็บประวัติไว้ ข้อเสนอคือไม่คืนสิทธิ์ผูกเดิมอัตโนมัติหากภายหลังสถานะย้อนกลับเป็น `0` ให้เจ้าหน้าที่ตรวจและอนุมัติใหม่ก่อน

คำขอเชื่อมต่อที่ยื่นแล้วไม่ถูกยกเลิกหรือลบทิ้งอัตโนมัติ เจ้าหน้าที่ดำเนินการต่อได้ตามสิทธิ์ ส่วนผู้ประกอบการอ่านหรือแก้ไขได้ตามสิทธิ์ปัจจุบัน งาน sync นี้ไม่เปลี่ยนสถานะคำขอหรือจุดเชื่อมต่อ current/live

## 4. การอัปเดตสถานะจาก Fac60k ทุกวัน

### รอบและขอบเขต

- ตรวจโรงงานเข้าข่ายที่ยังไม่ถูกลบทั้งหมดวันละครั้ง โดยอ่านเฉพาะ identifiers และสถานะที่จำเป็นจาก Fac60k ไม่ต้องคัดลอกข้อมูลทั้งชุด 60k เข้าระบบใหม่
- กำหนดเวลาตาม `Asia/Bangkok` หลังรอบอัปเดตต้นทางเมื่อยืนยันรอบนั้นได้ เวลาเริ่มงานจริงยังต้องกำหนดก่อนเปิดใช้
- ชุดแรกอัปเดตเฉพาะสถานะประกอบกิจการจากทะเบียนต้นทาง พร้อมเวลาที่ตรวจสำเร็จล่าสุด
- จับคู่ด้วย identity ที่ยืนยันแล้ว หากเลขทะเบียนเปลี่ยน จับคู่ไม่ได้ หรือพบหลายแถวขัดแย้ง ให้พักรายการเพื่อตรวจสอบ ไม่ซ่อม identity อัตโนมัติ
- อ่านได้ทุกสถานะ โดยเฉพาะ `FFLAG = 2` ไม่ใช้ตัวกรอง candidate `0`, `1`, `3` กับงานนี้

### ขั้นตอน

1. สร้างบันทึกรอบงานและป้องกันงานรันซ้อนกัน
2. อ่านรายการเป้าหมายเป็นชุดและค้นสถานะต้นทาง โดยลดการ query ทีละโรงงาน
3. ตรวจความถูกต้องของการจับคู่และแปลง `FFLAG` ตาม mapping เดิม
4. บันทึกสถานะใหม่เฉพาะรายการที่เปลี่ยน พร้อมประวัติค่าเดิม/ใหม่ ที่มา และเวลาตรวจพบ; ถ้าต้นทางไม่มีเวลาเปลี่ยนจริง ห้ามใช้เวลาตรวจพบแทนโดยอ้างว่าเป็นเวลาเปลี่ยนจริง
5. ประเมินผลต่อรายการผูกเพิ่มเติมใน transaction ที่สอดคล้องกับการเปลี่ยนสถานะ ป้องกันการใช้สถานะเก่าหรือผลตรวจเก่าเขียนย้อนข้อมูลใหม่
6. เก็บสรุปจำนวนที่ตรวจสำเร็จ ไม่เปลี่ยน เปลี่ยนสถานะ ไม่พบต้นทาง กำกวม และล้มเหลว พร้อม retry เฉพาะงานที่ยังไม่สำเร็จ

การรันซ้ำต้องไม่สร้างประวัติเปลี่ยนสถานะหรือรายการสิ้นสุดสิทธิ์ซ้ำโดยไม่มีการเปลี่ยนจริง การ retry ต้องไม่คืนสิทธิ์ที่เจ้าหน้าที่เพิกถอนไว้

### ข้อมูลที่ไม่เขียนทับในรอบแรก

- ชื่อ ที่อยู่ พิกัด และข้อมูลทั่วไปที่ผ่านการแก้ไข/อนุมัติใน POMS: ตรวจความต่างได้ แต่ยังไม่เขียนทับจนกว่าจะกำหนดเจ้าของข้อมูลราย field
- การเลือกเข้า/ออกจากรายการโรงงานเข้าข่าย ข้อมูล EIA โครงการ ผู้ติดต่อ เอกสาร และจุดตรวจวัด: ไม่เปลี่ยนจากการ sync สถานะ
- `factories`, สถานะคำขอ และ active connected points: ไม่อัปเดตโดยอนุมานจากการเปลี่ยนสถานะใน Fac60k

แหล่งสถานะอ้างอิงต้องเป็นจุดเดียวกันทั้งในหน้ารายการและการตรวจสิทธิ์ ก่อนพัฒนาต้องตรวจว่าการเปิด canonical factory profiles ในสภาพแวดล้อมนั้นอ่าน/เก็บสถานะที่ใด เพื่อไม่สร้างค่าสถานะอีกชุดที่ขัดกัน ดู [คู่มือข้อมูลทั่วไปโรงงาน](./factory-profile-consistency-rollout.md)

### ความสดและกรณีต้นทางขัดข้อง

งานประจำวันช่วยให้ข้อมูลทั่วไปทันรอบ แต่ไม่รับประกันการเปลี่ยนสิทธิ์ทันทีหลังต้นทางแก้ไข จึงตรวจสถานะเฉพาะโรงงานที่ผูกเพิ่มตอน login และก่อนทำรายการที่ใช้สิทธิ์นี้ หากเวลาตรวจสำเร็จล่าสุดเกินอายุที่กำหนดให้ตรวจต้นทางซ้ำ

ข้อเสนอเมื่อข้อมูลเก่าและอ่านต้นทางซ้ำไม่ได้คือคงสถานะและประวัติเดิมไว้ แต่ยังไม่ให้ทำรายการที่ต้องพึ่งสิทธิ์ผูกพิเศษจนกว่าจะยืนยันได้ ไม่ปฏิเสธการยืนยันตัวตนหรือสิทธิ์โรงงานอื่นที่ตรวจได้ตาม flow เดิม ความล้มเหลวต้องไม่ถูกบันทึกเป็นการจำหน่ายทะเบียนหรือการเพิกถอนถาวร

ต้องแยกเวลาลองตรวจล่าสุดออกจากเวลาตรวจสำเร็จล่าสุด เพื่อไม่ให้การ retry ที่ล้มเหลวทำให้ข้อมูลดูเหมือนใหม่ อายุข้อมูลสูงสุดและ timeout/retry เป็นค่าที่ต้องยืนยันก่อนเปิดใช้ ความสดยังขึ้นกับรอบที่ Fac60k ต้นทางได้รับการอัปเดตด้วย

## ลำดับการพัฒนาในงานถัดไป

1. ยืนยัน permission ผู้จัดการรายการผูก รูปแบบหลักฐาน อายุข้อมูลสูงสุด เวลางานรายวัน และนโยบายสถานะที่ตรวจไม่ได้
2. ออกแบบ schema รายการผูก ประวัติสถานะ และผลรอบงาน พร้อมการป้องกันซ้ำ/แก้พร้อมกัน
3. ทำตัวอ่านสถานะทุก `FFLAG` และตัวประเมินสิทธิ์กลาง โดยไม่ใช้ candidate filter แทน
4. เพิ่มการให้/เพิกถอนสิทธิ์และตรวจเงื่อนไข `ยังไม่แจ้งประกอบ` ที่ backend
5. เชื่อมรายชื่อหลัง login, persona resolution, `/auth/me` และทุก action ที่อาศัยสิทธิ์โรงงาน รวมถึงคำขอที่อ้างอิงโรงงานเข้าข่ายโดยไม่มี factory master จาก i-industry
6. ทดลองงานรายวันแบบรายงานความต่างก่อนเขียนจริง ตรวจการจับคู่และผลกระทบต่อรายการผูก แล้วจึงเปิดใช้ตามขั้นตอน release ที่ได้รับอนุมัติ
7. อัปเดต canonical API docs และ runtime OpenAPI ใน change เดียวกับ client-visible behavior; หลัง production deployment ตรวจ contract ที่เผยแพร่จริงตามกติกาโครงการ

การทดลองแบบรายงานความต่างไม่ถือว่าเปิดใช้การอัปเดตสถานะหรือ flow ใหม่สำเร็จ ต้องทดสอบครบทั้งการยืนยันตัวตน การได้สิทธิ์ และการทำรายการก่อน release

## เกณฑ์ตรวจรับสำหรับ implementation

- [ ] ผูกได้เฉพาะโรงงานเข้าข่ายที่ยังไม่ถูกลบและยืนยันสถานะ `0` ได้; ปฏิเสธสถานะ `1`, `2`, `3` และสถานะที่ยืนยันไม่ได้
- [ ] ผู้ไม่มี permission จัดการรายการผูกให้ตนเองหรือผู้อื่นไม่ได้; ป้องกันการผูกซ้ำและเก็บผู้ดำเนินการจริง
- [ ] กรณี A, B จาก flow เดิมและ C จากรายการผูก ได้ A, B, C และยื่นคำขอกับ C ได้ตาม permission/validation ของคำขอ
- [ ] Provider ยืนยันตัวตนสำเร็จแต่ไม่ส่งโรงงานหรือนิติบุคคล ยังเข้าแบบ operator ได้เมื่อมีรายการผูกที่ใช้ได้; citizen persona และกรณียืนยันตัวตนไม่ผ่านไม่ถูกข้ามกติกาเดิม
- [ ] โรงงานเดียวปรากฏจากสองแหล่งไม่ซ้ำ และไม่ให้สิทธิ์โรงงานอื่นในนิติบุคคลเดียวกันโดยอาศัยรายการผูกรายโรงงาน
- [ ] ตัวระบุใน response และ `ownedFactoryIds` รักษาความหมายเดิม ไม่ใช้ eligible row ID แทน FID
- [ ] Login, `/auth/me`, รายการโรงงาน และ action ของคำขอตรวจสิทธิ์สอดคล้องกัน; สิทธิ์ที่สิ้นสุดมีผลกับ token เดิมในการเรียกครั้งถัดไป
- [ ] เปลี่ยน `0 → 1` แล้วมี/ไม่มีสิทธิ์จาก i-industry ให้ผลตามตาราง และไม่ยกเลิกคำขอเดิมอัตโนมัติ
- [ ] งานรายวันตรวจพบ `0 → 2` และ `0 → 3` ได้ แม้ candidate endpoint ไม่คืนสถานะ `2`
- [ ] สถานะย้อนกลับ `1 → 0` ไม่คืนรายการผูกที่สิ้นสุดแล้วเองตามข้อเสนอในแผน
- [ ] ต้นทางล่ม ไม่พบแถว สถานะไม่รู้จัก และการจับคู่กำกวม ไม่ลบข้อมูลหรือเปลี่ยนเป็นจำหน่ายทะเบียน; ใช้นโยบายความสดก่อนอนุญาตสิทธิ์พิเศษ
- [ ] รันซ้ำ รันซ้อน และตรวจสถานะพร้อม login/ให้สิทธิ์/เพิกถอน ไม่ทำให้ข้อมูลเก่าเขียนทับใหม่หรือคืนสิทธิ์ที่ถูกเพิกถอน
- [ ] ชื่อ ที่อยู่ ข้อมูลเฉพาะ POMS สถานะคำขอ และ connected points ไม่ถูกเขียนทับจากงาน sync นี้
- [ ] ตรวจ contract docs/OpenAPI ให้ตรงกับพฤติกรรมจริง และรัน backend typecheck กับ tests ที่เกี่ยวข้องในงาน implementation
