# คู่มืออีเมลแจ้งเตือนมลพิษ

[กลับไปคู่มือ Backend](./README.md) · [API อีเมลแจ้งเตือน](../api/menus/notifications/email-notifications.md)

การติดตั้ง code ไม่เปิดส่งอีเมลโดยอัตโนมัติ `ALERT_EMAIL_ENABLED` เริ่มต้นเป็น `false` และก่อนเปิดต้องกำหนดตัวเลือกธุรกิจครบ การเปิดใช้ SMTP และ migration ในสภาพแวดล้อมจริงเป็นขั้นตอนแยกจากการทดสอบในเครื่อง

## รอบและประเภทอีเมล

เวลาทั้งหมดใช้ `Asia/Bangkok` อีเมลรายชั่วโมงแสดงชั่วโมงตรวจวัดที่สิ้นสุดแล้ว ส่วนรายวันใช้วันที่ก่อนหน้ารอบ 09:00 น.

| กรณี | ประเภทเหตุการณ์ | รอบ | เกณฑ์ |
| --- | --- | --- | --- |
| 1 | `STANDARD_EXCEEDED` | ทุกชั่วโมง | เหตุการณ์ค่าเกินมาตรฐานที่ integration ส่งมา |
| 2 | `EIA_EXCEEDED` | ทุกชั่วโมง | เหตุการณ์ค่าเกินค่าควบคุม EIA ที่ integration ส่งมา |
| 3 | `DAILY_COMPLETENESS_LOW` | ทุกวัน 09:00 น. | รายงานของพารามิเตอร์ต่ำกว่า 80% ของวันก่อนหน้า |
| 4 | `CONSECUTIVE_NO_REPORT`, `CEMS` | ทุกวัน 09:00 น. | ไม่รายงานหรือรายงานต่ำกว่า 80% ต่อเนื่องอย่างน้อย 15 วัน |
| 5 | `CONSECUTIVE_NO_REPORT`, `WPMS` | ทุกวัน 09:00 น. | ไม่รายงานหรือรายงานต่ำกว่า 80% ต่อเนื่องอย่างน้อย 8 วัน; แสดงชื่อ BOD/COD Online |
| 6 | `ABNORMAL_VALUE` | ทุกวัน 09:00 น. | ค่านิ่ง ศูนย์ หรือติดลบตามจำนวนค่ารายชั่วโมงต่อเนื่องที่กำหนด |

หากช่วงตรวจวัดเป็น 11:00–11:59:59 น. รอบที่ส่งได้คือหลัง 12:00 น. เช่น 12:05 น. เมื่อกำหนด delay 5 นาที ตัวเลข 11:00 ในรายการคือเวลาเริ่มตรวจวัด ไม่ใช่เวลาส่งอีเมล

กรณี 1–2 ใช้เหตุการณ์ที่ส่งผ่าน [Integration Alert Events](../api/integrations/alert-events/README.md) ไม่สร้างเกณฑ์มลพิษขึ้นเองจากค่า default ของหน้า dashboard การนับข้อมูลรายวันแยกตามจุด พารามิเตอร์ และหน่วย ข้อมูลต้นทางที่อ่านไม่ได้ต้องถูกจัดเป็น source error และห้ามแปลงเป็นวันไม่มีรายงาน

Worker มองย้อนหลังรายชั่วโมง 24 ชั่วโมงเพื่อจัดเหตุการณ์ที่เข้ามาช้า หากเหตุการณ์เก่ากว่านั้นต้องตรวจและวางแผน backfill แยก ไม่มีการส่งย้อนหลังเกินขอบเขตนี้โดยอัตโนมัติ รายวันคำนวณวันที่ล่าสุดที่ถึงรอบ 09:00 แล้ว และเมื่อ restart สามารถคำนวณซ้ำได้โดย outbox กันเหตุการณ์/ผู้รับซ้ำ

## ตัวเลือกก่อนเปิดใช้

ตารางนี้เป็นตัวเลือกที่ code รองรับ ไม่ใช่การยืนยันว่าผู้ใช้เลือกค่าใดแล้ว ค่าเปิดใช้และนโยบายถูกตรวจด้วย [policy reader](../../../backend/src/modules/alert-emails/alert-email-policy.ts) เมื่อ `ALERT_EMAIL_ENABLED=true` แล้วค่าขาดหรือผิดรูปแบบจะไม่ผ่าน validation

| Setting | Accepted value | ผลต่อพฤติกรรม |
| --- | --- | --- |
| `ALERT_EMAIL_ENABLED` | `false` / `true` | ไม่ระบุเท่ากับ `false`; `true` ต้องมีค่าต่อไปนี้ครบ |
| `ALERT_EMAIL_RECIPIENT_MODE` | `POINT_OFFICERS` / `POINT_OFFICERS_AND_FACTORY` | ใช้อีเมลเจ้าหน้าที่ของจุด หรือรวมอีเมลโรงงานของจุดด้วย |
| `ALERT_EMAIL_COMPLETENESS_POLICY` | `ON_TIME` / `NORMAL_EXCLUDING_SHUTDOWN` | เลือกสูตรนับรายงานครบ |
| `ALERT_EMAIL_EXEMPT_DAY_POLICY` | `RESET` / `PAUSE` | วันยกเว้นที่ไม่มี expected hour จะจบ streak หรือพัก streak |
| `ALERT_EMAIL_DAILY_FORMAT` | `BY_TYPE` | แยกอีเมลตามประเภท; กรณีต่อเนื่องแยก CEMS/WPMS |
| `ALERT_EMAIL_ABNORMAL_MODE` | `PREVIOUS_DAY` | ตรวจเหตุการณ์ผิดปกติในข้อมูลรายวันก่อนหน้า |
| `ALERT_EMAIL_ABNORMAL_READINGS` | integer 2–168 | จำนวนค่ารายชั่วโมงต่อเนื่องที่ยืนยันความผิดปกติ; จำนวน 5 ยังต้องยืนยันก่อนเปิดใช้ |
| `ALERT_EMAIL_HOURLY_DELAY_MINUTES` | integer 0–59 | นาทีหลังต้นชั่วโมงที่ข้อมูลครบแล้วจึงถึงรอบรายชั่วโมง |

สูตร `ON_TIME` ใช้จำนวนชั่วโมงที่มีค่าตรวจวัดและรายงานทันเวลาหาร 24; `NORMAL_EXCLUDING_SHUTDOWN` ใช้ชั่วโมงที่มีค่าตรวจวัดสถานะ `Normal` หารด้วย 24 ลบชั่วโมง `Shut Down` ไม่ใช้จำนวน row เพราะข้อมูลซ้ำในชั่วโมงหนึ่งนับได้เพียงหนึ่งชั่วโมง การตัดสินต่ำกว่า 80% ใช้สัดส่วนจริงก่อนปัดตัวเลขแสดงผล

เมื่อ expected count เป็นศูนย์ วันนั้นเป็นวันยกเว้น ไม่ใช่ 0% และให้ใช้ `RESET` หรือ `PAUSE` ตามที่กำหนดไว้ วันที่รายงานได้อย่างน้อย 80% จบ streak ส่วนวันที่ summary ขาดจะไม่ถูกสมมติให้เป็นวันรายงานต่ำ

แม้ `PAUSE` จะเก็บ streak เดิมไว้ วันยกเว้นเองไม่สร้างอีเมลรายงานต่ำหรือรายงานไม่ครบต่อเนื่อง การนับเริ่มที่วันเต็มหลังวันเริ่มใช้งานของแต่ละพารามิเตอร์ หากไม่ทราบ `connectedAt` หรือไม่พบเวลาของ device configuration ที่ยืนยันพารามิเตอร์นั้น จะข้ามการสร้างเหตุการณ์รายวันแทนการเดาประวัติ

วันเริ่มใช้งาน (`activatedAt`) ใช้เวลาที่ใหม่กว่าระหว่าง `connectedAt` ของจุด กับ `updatedAt` ของ device configuration revision ล่าสุดที่ตรง `deviceCode` และ channel `dataType` ของพารามิเตอร์พร้อมหน่วย วิธีนี้ป้องกันการเพิ่มพารามิเตอร์วันนี้แล้วนับช่วงก่อนเพิ่มว่าไม่รายงาน แต่มีข้อจำกัดว่าแก้ configuration อาจเริ่มนับวันใหม่แม้ channel เดิมยังใช้งานอยู่ เพราะระบบยังไม่มี timestamp ประวัติการเปิดใช้ราย channel ให้ยืนยันย้อนหลัง

การหาจำนวนวันต่อเนื่องอ่านย้อนถึงวันเริ่มใช้งานนี้ เป็น query ช่วงละ 30 วัน ไม่ตัดตัวเลขให้เหลือ 15/8 วันและไม่สมมติจำนวนวันเกินข้อมูลที่มี หากโหลดข้อมูลมากกว่า 100,000 rows จะหยุดเป็น source error เพื่อให้ตรวจสภาพข้อมูลก่อนดำเนินการ

การจัดคิวรายวันรับเฉพาะ candidate IDs ที่การเตรียมข้อมูลสำเร็จภายใต้นโยบายปัจจุบัน ไม่ดึง daily alert เก่าที่สร้างด้วยนโยบายอื่นหรือเตรียมข้อมูลไม่สำเร็จมาส่งแทน

ข้อมูลซ้ำในชั่วโมงเดียวเลือกค่าที่ใช้ได้ก่อนค่าที่เป็น `null`; หากมีค่าตัวเลขที่ขัดแย้งกัน ชั่วโมงนั้นยังใช้ประเมินความครบถ้วนได้ แต่ไม่ใช้ยืนยันลำดับค่าผิดปกติ เวลาเริ่มและเวลายืนยันความผิดปกติในอีเมลใช้ timestamp ของค่าต้นฉบับ ส่วนการตรวจความต่อเนื่องใช้ชั่วโมงตรวจวัด

ความผิดปกติใช้เฉพาะค่าตัวเลขที่ finite และสถานะ `Normal` ชั่วโมงที่หายหรือสถานะอื่นตัดลำดับ ค่าศูนย์และค่าติดลบแยกจากค่านิ่ง; ค่าติดลบต่อเนื่องอาจมีตัวเลขต่างกันได้ และค่านิ่งเปรียบเทียบค่าที่เท่ากันจริง ห้าค่ารายชั่วโมงมีระยะจากค่าแรกถึงค่าที่ยืนยันสี่ชั่วโมง เนื้อหาอีเมลแสดงจำนวนค่าและระยะเวลาแยกกัน

โหมด `PREVIOUS_DAY` รวมลำดับที่ยืนยันแล้วและยังมีค่าผิดปกติในวันก่อนหน้า แม้ค่าแรกจะเริ่มในวันก่อนหน้านั้น การเกิดลำดับเดิมต่อเนื่องหลายวันจึงมีเหตุการณ์รายวันแยกตามวันที่ตรวจสอบ ตามนโยบายที่ต้องยืนยันก่อนเปิดใช้

## ผู้รับและ CC

- ต้องเลือกนโยบายผู้รับหลักก่อนเปิดใช้ ไม่ผูกผู้รับจากผู้ใช้ทุกคนที่มีสิทธิ์ดูการแจ้งเตือน
- ข้อมูลโรงงาน current/live POMS ใช้ active connected measurement point ใน `cems_wpms_connected_measurement_points`; `factories` เป็นข้อมูล identity/access ประกอบ
- `officer_notification_emails_json` และ `notification_emails_json` ของ connected point เป็นข้อมูลปัจจุบัน ค่า `null` จึงใช้ข้อมูลคำขอต้นทางได้ แต่ `[]` หมายถึงล้างผู้รับแล้วและห้าม fallback
- จัด delivery ต่อผู้รับหลัก และรวมเฉพาะเหตุการณ์ของจุดที่ผู้รับนั้นรับได้ ไม่ส่งข้อมูลโรงงานอื่นรวมไปเพราะใช้รอบเดียวกัน
- ทุกฉบับต้องมี CC `diw.iemc@gmail.com`; normalize และกันอีเมลซ้ำใน envelope
- ก่อนส่ง worker ตรวจว่าผู้รับยังรับเหตุการณ์ชุดนั้นได้ ถ้าขอบเขตเปลี่ยนจะบันทึก `SKIPPED`
- เหตุการณ์สถานะ `DISMISSED` ไม่ถูกจัดคิวส่ง และ worker ตรวจสถานะอีกครั้งก่อนส่งรายการที่เคยจัดคิวแล้ว

## คิวและผล SMTP

Outbox เก็บเนื้อหา ผู้รับ รอบ และ event IDs เป็น snapshot ด้วยตาราง `alert_email_batches`, `alert_email_batch_events` และ `alert_email_deliveries` migration อยู่ที่ [`0127_create_alert_email_outbox.ts`](../../../backend/src/db/migrations/0127_create_alert_email_outbox.ts)

การกันซ้ำมีทั้ง key ของ batch และคู่เหตุการณ์กับผู้รับใน cadence เดียวกัน จึงไม่จัดเหตุการณ์เดิมส่งซ้ำเมื่อ worker restart หรือเมื่อชุดใหม่มีเหตุการณ์เก่าปนกับเหตุการณ์ที่เข้ามาภายหลัง การ claim ใช้การอัปเดตแบบ atomic และมี lease token เพื่อไม่ให้สอง worker ส่งรายการเดียวกัน

| เหตุการณ์ | การจัดการ |
| --- | --- |
| SMTP ยอมรับทุกผู้รับ | `SMTP_ACCEPTED`; ต้องใช้ bounce/provider evidence เพิ่มถ้าต้องการยืนยันว่าถึง inbox |
| SMTP ตอบ 4xx โดยยังไม่ยอมรับผู้รับ | `RETRY_PENDING`; backoff 1, 2, 4, 8 นาที และไม่เกิน 5 attempts |
| SMTP ตอบ 5xx | `FAILED` |
| SMTP ยอมรับเพียงบางผู้รับ | `FAILED` พร้อมรายการ accepted/rejected; ไม่ส่งซ้ำทั้ง envelope |
| Timeout/ผลไม่ชัด หรือ lease หมดหลังเริ่มงาน | `UNKNOWN`; ไม่ลองใหม่อัตโนมัติเพราะอาจส่งสำเร็จแล้ว |
| ตรวจขอบเขตผู้รับไม่ได้ | retry ได้เฉพาะขั้นก่อนส่ง และจำกัด attempts เช่นเดียวกัน |

หากได้ `UNKNOWN` ต้องตรวจ log/provider ด้วย message ID และข้อมูลที่ปกปิดแล้วก่อนตัดสินใจดำเนินการ ไม่มี public API สำหรับ resend ในงานนี้ สถานะ SMTP แยกจาก `AUTO`, `OFFICER`, `ACKNOWLEDGED`, `DISMISSED` ของการติดตามเหตุการณ์

## ตรวจรับก่อนเปิดสภาพแวดล้อมจริง

1. ยืนยันผู้รับหลัก สูตร 80% นโยบายวันยกเว้น จำนวนค่าต่อเนื่อง และเวลาที่ข้อมูลรายชั่วโมงพร้อมก่อนกำหนด settings
2. ตรวจ migration และ dependency ของแหล่งค่าตรวจวัดในสภาพแวดล้อมทดสอบ พร้อมทวน `connectedAt` และ device configuration `updatedAt` ของ channel เดิมว่ารองรับวันที่เริ่มนับที่ต้องการ ห้ามใช้แหล่งข้อมูลที่อ่านไม่ได้แทน 0 รายงาน
3. ใช้ preview API ตรวจครบหกกรณี พร้อมพารามิเตอร์ชื่อเดียวกันแต่ต่างหน่วย โรงงานหลายแห่ง และช่วงข้ามวัน
4. ทดสอบ transport จำลองให้ครอบคลุมยอมรับครบ ปฏิเสธชั่วคราว/ถาวร ยอมรับบางผู้รับ และ timeout ก่อนเปิด SMTP จริง
5. ตรวจ [TDD evidence](../evidence/notifications/alert-email.tdd.md) และ runtime `/api/v1/openapi.json` ให้ตรงกับ contract เมื่อมีการ deploy ที่ได้รับอนุญาต

ไม่เก็บ credential SMTP, database หรือ API key ในเอกสาร ไม่ใช้ log raw payload ที่มีอีเมล/ข้อมูลติดต่อเพื่อวิเคราะห์ผล
