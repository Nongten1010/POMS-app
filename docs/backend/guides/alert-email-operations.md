# คู่มืออีเมลแจ้งเตือนมลพิษ

[กลับไปคู่มือ Backend](./README.md) · [API อีเมลแจ้งเตือน](../api/menus/notifications/email-notifications.md)

การติดตั้ง code ไม่เปิดส่งอีเมลโดยอัตโนมัติ `ALERT_EMAIL_ENABLED` เริ่มต้นเป็น `false` และก่อนเปิดต้องกำหนดตัวเลือกธุรกิจครบ การเปิดใช้ SMTP และ migration ในสภาพแวดล้อมจริงเป็นขั้นตอนแยกจากการทดสอบในเครื่อง

## รอบและประเภทอีเมล

เวลาทั้งหมดใช้ `Asia/Bangkok` [แม่แบบข้อความทั้ง 6 แบบ](../api/menus/notifications/email-notifications.md#รูปแบบข้อความตาม-pdf) ใช้จดหมายตามคอลัมน์อีเมลใน PDF เรื่องกรณี 1–2 แสดงวันที่ตรวจวัดและเวลาเริ่มตรวจวัด `HH.mm` ของชั่วโมงที่สิ้นสุดแล้ว ส่วนเรื่องรายวันข้อ 3–5 แสดงวันที่ข้อมูลก่อนหน้ารอบ 09:00 น. ในรูปแบบ `d-m-พ.ศ.` ไม่แสดงเวลารอบส่งแทนเวลาตรวจวัด

| กรณี | ประเภทเหตุการณ์ | รอบ | เกณฑ์ |
| --- | --- | --- | --- |
| 1 | `STANDARD_EXCEEDED` | ต้นชั่วโมง เช่น 12:00, 13:00, 14:00 น. เมื่อ delay เป็น 0 | เหตุการณ์ค่าเกินมาตรฐานจาก integration หรือ detector ภายในที่เปิด active |
| 2 | `EIA_EXCEEDED` | ต้นชั่วโมง เช่น 12:00, 13:00, 14:00 น. เมื่อ delay เป็น 0 | เหตุการณ์ค่าเกินค่าควบคุม EIA จาก integration หรือ detector ภายในที่เปิด active |
| 3 | `DAILY_COMPLETENESS_LOW` | ทุกวัน 09:00 น. | รายงานของพารามิเตอร์ต่ำกว่า 80% ของวันก่อนหน้า |
| 4 | `CONSECUTIVE_NO_REPORT`, `CEMS` | ทุกวัน 09:00 น. | ไม่รายงานหรือรายงานต่ำกว่า 80% ต่อเนื่องอย่างน้อย 15 วัน |
| 5 | `CONSECUTIVE_NO_REPORT`, `WPMS` | ทุกวัน 09:00 น. | ไม่รายงานหรือรายงานต่ำกว่า 80% ต่อเนื่องอย่างน้อย 8 วัน; แสดงชื่อ BOD/COD Online |
| 6 | `ABNORMAL_VALUE` | ทุกชั่วโมง เมื่อครบเกณฑ์ | ค่านิ่ง ศูนย์ หรือติดลบต่อเนื่องอย่างน้อย 5 ชั่วโมงจริง; แจ้ง 1 ครั้งต่อพารามิเตอร์/หน่วย/จุด/วัน |

กรณี 1–2 ตั้ง `ALERT_EMAIL_HOURLY_DELAY_MINUTES=0` สำหรับรอบที่ผู้ใช้กำหนด 12:00, 13:00, 14:00 น. หากช่วงตรวจวัดเป็น 11:00–11:59:59 น. และระบบรับเหตุการณ์ภายในรอบ 12:00 น. จะเริ่มจัดคิวและส่งในรอบ 12:00 น. เรื่องอีเมลยังแสดง `เวลา 11.00 น.` ตามเวลาเริ่มตรวจวัด ส่วนรายวันข้อมูลวันที่ 4 ตุลาคมส่งวันที่ 5 ตุลาคม 09:00 น. เรื่องแสดง `ในวันที่ 4-10-2569`

Worker ตั้ง timer ตรวจคิวที่ต้นนาทีของนาฬิกา และจัดคิวรายชั่วโมงของกรณี 1–2 ใหม่อิงนาทีรอบที่กำหนด โดยคงชุดเหตุการณ์ที่มี `detectedAt` ไม่เกินเวลาเริ่มรอบนั้น ข้อมูลของช่วง 11:00 น. ที่เข้ามาตอน 12:06 น. รอรอบ 13:00 น. และยังแสดงเวลาตรวจวัด `11.00` เมื่อ restart จะตรวจงานทันที แต่หากเป็นนาทีนอกรอบจะไม่สร้างคิวรายชั่วโมงใหม่

สำหรับกรณี 1–2 หาก callback ของ timer ทำงานช้า เช่น timer รอบ 12:00 น. ได้ทำงานจริงตอน 12:01 น. ระบบยังใช้รอบและ cutoff 12:00 น. หาก worker ยังส่งงานก่อนหน้าอยู่ จะเก็บรอบรายชั่วโมงล่าสุดที่ถึงเวลาไว้และเริ่มเมื่อ worker ว่าง โดยไม่ทำงานซ้อน การเริ่มส่งจึงอาจช้ากว่ารอบที่ตั้งไว้เมื่อ SMTP หรืองานก่อนหน้ายังไม่จบ แต่ไม่เลื่อนเหตุการณ์หลัง cutoff เข้ามารวมในรอบเดิม การรับเข้า Inbox ขึ้นอยู่กับ SMTP และระบบเมลผู้รับด้วย

แต่ละรอบอาจมีหลายอีเมลเพราะแยกประเภท ผู้รับ วันที่ และช่วงตรวจวัด เช่น รอบ 13:00 น. อาจมีทั้งข้อมูล 12:00 น. และข้อมูล 11:00 น. ที่มาช้าในคนละฉบับ เพื่อคงเวลาในเรื่องตรงกับเนื้อหา การ retry ของ delivery ที่ส่งไม่สำเร็จใช้ backoff เดิมและอาจเกิดระหว่างรอบได้

กรณี 1–2 ใช้เหตุการณ์ที่ส่งผ่าน [Integration Alert Events](../api/integrations/alert-events/README.md) หรือ [ตัวตรวจค่าเกินภายใน](./hourly-exceedance-detector.md) ที่เปิด active ตาม allowlist ไม่สร้างเกณฑ์มลพิษขึ้นเองจากค่า default ของหน้า dashboard การนับข้อมูลรายวันแยกตามจุด พารามิเตอร์ และหน่วย ข้อมูลต้นทางที่อ่านไม่ได้ต้องถูกจัดเป็น source error และห้ามแปลงเป็นวันไม่มีรายงาน

กรณี 1–2 worker มองย้อนหลังรายชั่วโมง 24 ชั่วโมงเพื่อจัดเหตุการณ์ที่เข้ามาช้าในรอบถัดไป หากเหตุการณ์เก่ากว่านั้นต้องตรวจและวางแผน backfill แยก ไม่มีการส่งย้อนหลังเกินขอบเขตนี้โดยอัตโนมัติ รายวันข้อ 3–5 คำนวณวันที่ล่าสุดที่ถึงรอบ 09:00 แล้ว ส่วนกรณี 6 ใช้ข้อมูลที่มีถึงเวลาตรวจของวันปัจจุบัน เมื่อ restart สามารถคำนวณซ้ำได้โดย identity ของเหตุการณ์และ outbox กันการแจ้งซ้ำ

## ตัวเลือกก่อนเปิดใช้

ตารางนี้เป็นตัวเลือกที่ code รองรับ ส่วนเกณฑ์ `ABNORMAL_VALUE` ถูกกำหนดตายตัวเป็นรายชั่วโมงและ 5 ชั่วโมงจริง การตั้งค่าผู้รับและสูตรรายงานครบยังต้องกำหนดก่อนเปิดใช้ ค่าเปิดใช้และนโยบายถูกตรวจด้วย [policy reader](../../../backend/src/modules/alert-emails/alert-email-policy.ts) เมื่อ `ALERT_EMAIL_ENABLED=true` แล้วค่าขาดหรือผิดรูปแบบจะไม่ผ่าน validation

| Setting | Accepted value | ผลต่อพฤติกรรม |
| --- | --- | --- |
| `ALERT_EMAIL_ENABLED` | `false` / `true` | ไม่ระบุเท่ากับ `false`; `true` ต้องกำหนดนโยบายผู้รับ ความครบถ้วน วันยกเว้น รูปแบบรายวัน และ delay |
| `ALERT_EMAIL_RECIPIENT_MODE` | `POINT_OFFICERS` / `POINT_OFFICERS_AND_FACTORY` | ใช้อีเมลเจ้าหน้าที่ของจุด หรือรวมอีเมลโรงงานของจุดด้วย |
| `ALERT_EMAIL_COMPLETENESS_POLICY` | `ON_TIME` / `NORMAL_EXCLUDING_SHUTDOWN` | เลือกสูตรนับรายงานครบ |
| `ALERT_EMAIL_EXEMPT_DAY_POLICY` | `RESET` / `PAUSE` | วันยกเว้นที่ไม่มี expected hour จะจบ streak หรือพัก streak |
| `ALERT_EMAIL_DAILY_FORMAT` | `BY_TYPE` | แยกอีเมลตามประเภท; กรณีต่อเนื่องแยก CEMS/WPMS |
| `ALERT_EMAIL_ABNORMAL_MODE` | legacy setting; ไม่จำเป็นต้องระบุ | ไม่ใช้ค่านี้อีก โหมดที่ทำงานเป็น `HOURLY` เสมอ แม้ environment เดิมยังเป็น `PREVIOUS_DAY` |
| `ALERT_EMAIL_ABNORMAL_READINGS` | legacy setting; ไม่จำเป็นต้องระบุ | ไม่ใช้ค่านี้ override เกณฑ์อีก เกณฑ์เป็นระยะเวลาอย่างน้อย 5 ชั่วโมงจริงและอย่างน้อย 6 ค่ารายชั่วโมง |
| `ALERT_EMAIL_HOURLY_DELAY_MINUTES` | integer 0–59 | นาทีของรอบส่งกรณี 1–2 ในแต่ละชั่วโมง; ใช้ 0 เพื่อเริ่มรอบตรงต้นชั่วโมง; `ABNORMAL_VALUE` ไม่รอ delay นี้ |

[ไฟล์ตัวอย่าง environment](../../../backend/.env.example) ปิดส่งด้วย `ALERT_EMAIL_ENABLED=false` และมีตัวอย่างนโยบายผู้รับ `POINT_OFFICERS`, `ON_TIME`, `RESET`, `BY_TYPE` และ delay 0; ค่า legacy สำหรับค่าผิดปกติไม่มีผลเปลี่ยนเกณฑ์รายชั่วโมงครบ 5 ชั่วโมงจริง ค่า `.env` จริงที่เดิมเป็น delay 5 ต้องเปลี่ยนเป็น `ALERT_EMAIL_HOURLY_DELAY_MINUTES=0` และ restart backend จึงเริ่มรอบตรงต้นชั่วโมง

สูตร `ON_TIME` ใช้จำนวนชั่วโมงที่มีค่าตรวจวัดและรายงานทันเวลาหาร 24; `NORMAL_EXCLUDING_SHUTDOWN` ใช้ชั่วโมงที่มีค่าตรวจวัดสถานะ `Normal` หารด้วย 24 ลบชั่วโมง `Shut Down` ไม่ใช้จำนวน row เพราะข้อมูลซ้ำในชั่วโมงหนึ่งนับได้เพียงหนึ่งชั่วโมง การตัดสินต่ำกว่า 80% ใช้สัดส่วนจริงก่อนปัดตัวเลขแสดงผล

เมื่อ expected count เป็นศูนย์ วันนั้นเป็นวันยกเว้น ไม่ใช่ 0% และให้ใช้ `RESET` หรือ `PAUSE` ตามที่กำหนดไว้ วันที่รายงานได้อย่างน้อย 80% จบ streak ส่วนวันที่ summary ขาดจะไม่ถูกสมมติให้เป็นวันรายงานต่ำ

แม้ `PAUSE` จะเก็บ streak เดิมไว้ วันยกเว้นเองไม่สร้างอีเมลรายงานต่ำหรือรายงานไม่ครบต่อเนื่อง การนับรายวันข้อ 3–5 เริ่มที่วันเต็มหลังวันเริ่มใช้งานของแต่ละพารามิเตอร์ หากไม่ทราบ `connectedAt` หรือไม่พบประวัติ activation ที่ตรงพารามิเตอร์และหน่วย จะข้ามการสร้างเหตุการณ์รายวันแทนการเดาประวัติ หากอ่านแหล่งประวัติไม่ได้จะเป็น source error

วันเริ่มใช้งาน (`activatedAt`) เก็บใน `alert_parameter_activations` แยกตาม live connected point พารามิเตอร์ และหน่วย การแก้ address, device, protocol หรือ config โดยยังมีพารามิเตอร์และหน่วยเดิมใน channel ปกติจะรักษาวันเริ่มเดิม การลบ channel ปิดช่วงใช้งาน เมื่อเพิ่มกลับจะเริ่มช่วงใหม่; Test mode เลิกใช้แล้วและไม่ปิด/กันช่วงใช้งานจาก flag เก่า การอนุมัติ `ADD_PARAMETER` รักษาประวัติของพารามิเตอร์เดิมได้เฉพาะจุดเดิมที่ยังเชื่อมต่อและตรงโรงงาน ระบบ และ station; พารามิเตอร์ใหม่เริ่มวันที่เพิ่มจริง และไม่ก่อน `connectedAt` ของจุดที่เชื่อมต่อใหม่

ต้องติดตั้ง migration [`0128_create_alert_parameter_activations.ts`](../../../backend/src/db/migrations/0128_create_alert_parameter_activations.ts) ก่อนใช้ backend รุ่นนี้ แม้ worker ยังปิดอยู่ เพราะเส้นทางบันทึก config และอนุมัติ connection อัปเดตประวัติใน transaction เดียวกัน Migration เติม baseline ครั้งเดียวด้วยเวลาที่ใหม่กว่าระหว่าง `connectedAt` กับ `updatedAt` ของ config ปัจจุบันที่ตรง channel ปกติ ไม่อนุมานประวัติต่อเนื่องจาก audit revision เก่า จึงต้องทวน baseline ในฐานข้อมูลทดสอบก่อนเปิดใช้จริง

เมื่อเลิกใช้ Test mode ต้องรัน [`0146_retire_device_channel_test_mode.ts`](../../../backend/src/db/migrations/0146_retire_device_channel_test_mode.ts) ด้วย โดยหยุด backend/Worker รุ่นเก่าที่เขียน `true` ก่อนเริ่ม migration. Migration ปรับ flag เก่าเป็น `false` รวม snapshot/ประวัติ และสร้างเฉพาะช่วง activation ที่ขาดของ current channel เดิมที่เคยเป็น Test mode และยังได้รับอนุมัติ โดยเริ่มนับที่เวลา UTC ที่ใหม่กว่าระหว่าง cutover กับ `connected_at` ของจุด จึงไม่เริ่มก่อน `connected_at` ไม่เดาประวัติย้อนหลังและไม่แก้วันเริ่มของช่วงเดิมที่มีอยู่. Worker ต้องโหลด config ใหม่ก่อนกลับมาทำงาน ดู [การเปลี่ยนผ่าน](../api/CHANGELOG.md#test-mode-retired)

หาก legacy audit ทำให้ baseline อยู่ในอนาคต ระบบจะรอถึง baseline นั้นก่อนเริ่มนับความผิดปกติ และรอถึงวันเต็มหลัง baseline ก่อนนับรายวันข้อ 3–5 ไม่เดา timezone เพื่อเลื่อนประวัติ การปิดช่วงใช้งานใช้เวลาที่ไม่น้อยกว่า baseline เพื่อให้ config ยังบันทึกได้อย่างสอดคล้องกับข้อจำกัดฐานข้อมูล

การหาจำนวนวันต่อเนื่องอ่านย้อนถึงวันเริ่มใช้งานนี้ เป็น query ช่วงละ 30 วัน ไม่ตัดตัวเลขให้เหลือ 15/8 วันและไม่สมมติจำนวนวันเกินข้อมูลที่มี หากโหลดข้อมูลมากกว่า 100,000 rows จะหยุดเป็น source error เพื่อให้ตรวจสภาพข้อมูลก่อนดำเนินการ

การจัดคิวรายวันรับเฉพาะ candidate IDs ที่การเตรียมข้อมูลสำเร็จภายใต้นโยบายปัจจุบัน ไม่ดึง daily alert เก่าที่สร้างด้วยนโยบายอื่นหรือเตรียมข้อมูลไม่สำเร็จมาส่งแทน

ข้อมูลซ้ำในชั่วโมงเดียวเลือกค่าที่ใช้ได้ก่อนค่าที่เป็น `null`; หากมีค่าตัวเลขที่ขัดแย้งกัน ชั่วโมงนั้นยังใช้ประเมินความครบถ้วนได้ แต่ไม่ใช้ยืนยันลำดับค่าผิดปกติ เวลาเริ่มและเวลาของค่าผิดปกติล่าสุดในอีเมลใช้ timestamp ของค่าต้นฉบับ ส่วนการตรวจความต่อเนื่องใช้ชั่วโมงตรวจวัด

## ค่าผิดปกติรายชั่วโมง

`ABNORMAL_VALUE` ใช้ข้อมูล `60m` แยกตามโรงงาน ระบบ จุดตรวจวัด พารามิเตอร์ และหน่วย ต้องเป็นตัวเลข finite และสถานะ `Normal` เท่านั้น ชั่วโมงที่หาย ค่า `null` สถานะอื่น หรือข้อมูลซ้ำที่ขัดแย้งกันตัดลำดับ การเปลี่ยนประเภทผิดปกติเริ่มลำดับใหม่ด้วย

| ประเภท | เงื่อนไข |
| --- | --- |
| `ZERO` | ค่า `0` ต่อเนื่อง |
| `NEGATIVE` | ค่าต่ำกว่า `0` ต่อเนื่อง ตัวเลขต่างกันได้ |
| `CONSTANT` | ค่าบวกเท่ากันจริงต่อเนื่อง ไม่มี tolerance |

แจ้งเมื่อมีอย่างน้อย 6 ค่ารายชั่วโมงต่อเนื่อง และระยะเวลาจากค่าต้นฉบับแรกถึงค่าที่ยืนยันไม่น้อยกว่า 5 ชั่วโมง เช่น 08:00–13:00 น. หาก timestamp เป็น 08:59–13:00 น. แม้อยู่ใน 6 ชั่วโมงตรวจวัดก็ยังไม่ครบ 5 ชั่วโมงจริง ต้องรอค่าถัดไปที่ผ่านเกณฑ์ ระยะเวลารวมในจดหมายตาม PDF คำนวณจาก `firstAbnormalAt` ถึง `endedAt` ของค่าผิดปกติล่าสุด ไม่ใช้ `confirmedAbnormalAt` หรือเวลารอบส่งเป็นเวลาสิ้นสุด หากไม่ได้บันทึก `endedAt` จะแสดงระยะเวลาไม่ระบุ; หาก timestamp ผิดรูปแบบหรือเวลาสิ้นสุดก่อนเวลาเริ่ม/เวลายืนยัน preview จะตอบ `400 BAD_REQUEST`

เมื่อครบเกณฑ์ ระบบจัดคิวในรอบรายชั่วโมงนั้นทันที ไม่รอ 09:00 น. หรือ `ALERT_EMAIL_HOURLY_DELAY_MINUTES`; worker ตรวจคิวทุกนาที จึงส่งเมื่อ worker รอบถัดไปประมวลผลและข้อมูลต้นทางพร้อม ไม่อ่านค่าที่ timestamp อยู่ในอนาคต `ABNORMAL_VALUE` เริ่มนับได้ตั้งแต่ activation จริงในวันแรก ไม่ต้องรอวันเต็มเหมือนการนับรายงานครบ

จำกัด 1 เหตุการณ์แจ้งเตือนต่อพารามิเตอร์/หน่วย/จุด/วันตามเวลาไทย โดยใช้ identity จุดที่คงเดิมเมื่อแทนแถว live point ไม่แยกโควตาตาม `ZERO`, `NEGATIVE`, `CONSTANT`, episode, activation หรือการแก้ config การกลับมาปกติแล้วผิดปกติใหม่ในวันเดียวกันจึงไม่แจ้งซ้ำ ผู้รับแต่ละคนรับเหตุการณ์นั้นได้ตามนโยบายและ outbox กันซ้ำข้ามการ restart

ลำดับความผิดปกติต่อข้ามเที่ยงคืนได้ โควตาเริ่มใหม่ที่วันไทยถัดไปและแจ้งในรอบแรกที่ยังเข้าเกณฑ์ โดยต้องมีค่าผิดปกติใหม่ของวันนั้นจริง ไม่ส่งซ้ำจากข้อมูลค้างของเมื่อวาน หากมีชั่วโมงขาดหรือสถานะไม่เข้าเงื่อนไขจะเริ่มนับลำดับใหม่ตามเดิม ดู [การเปลี่ยนผ่าน](../api/CHANGELOG.md#abnormal-hourly-five-hours)

## ผู้รับและ CC

- ต้องเลือกนโยบายผู้รับหลักก่อนเปิดใช้ ไม่ผูกผู้รับจากผู้ใช้ทุกคนที่มีสิทธิ์ดูการแจ้งเตือน
- ข้อมูลโรงงาน current/live POMS ใช้ active connected measurement point ใน `cems_wpms_connected_measurement_points`; `factories` เป็นข้อมูล identity/access ประกอบ
- `officer_notification_emails_json` และ `notification_emails_json` ของ connected point เป็นข้อมูลปัจจุบัน ค่า `null` จึงใช้ข้อมูลคำขอต้นทางได้ แต่ `[]` หมายถึงล้างผู้รับแล้วและห้าม fallback
- จัด delivery ต่อผู้รับหลัก และรวมเฉพาะเหตุการณ์ของจุดที่ผู้รับนั้นรับได้ ไม่ส่งข้อมูลโรงงานอื่นรวมไปเพราะใช้รอบเดียวกัน
- ทุกฉบับต้องมี CC `diw.iemc@gmail.com`; normalize และกันอีเมลซ้ำใน envelope
- ก่อนส่ง worker ตรวจผู้รับ จุด พารามิเตอร์ หน่วย และ activation ปัจจุบัน รวมถึง finite `measuredValue > thresholdValue` และ `thresholdType` ที่ตรงประเภทสำหรับ `STANDARD_EXCEEDED`/`EIA_EXCEEDED` หากเหตุการณ์ใดในชุดไม่ผ่าน จะบันทึก `SKIPPED` ทั้ง delivery ก่อนเรียก SMTP
- เหตุการณ์สถานะ `DISMISSED` ไม่ถูกจัดคิวส่ง และ worker ตรวจสถานะอีกครั้งก่อนส่งรายการที่เคยจัดคิวแล้ว

## คิวและผล SMTP

Outbox เก็บเนื้อหา ผู้รับ รอบ และ event IDs เป็น snapshot ด้วยตาราง `alert_email_batches`, `alert_email_batch_events` และ `alert_email_deliveries` migration อยู่ที่ [`0127_create_alert_email_outbox.ts`](../../../backend/src/db/migrations/0127_create_alert_email_outbox.ts)

การเปลี่ยนแม่แบบ PDF และกติกาจัดคิวตามรอบใช้กับ batch ที่สร้างใหม่ ไม่แก้ข้อความหรือ `scheduledAt` ใน batch เดิม ไม่ re-render และไม่ส่งซ้ำอัตโนมัติ หากมีอีเมลเดิมที่ยังรอส่ง ต้องทบทวน snapshot และสถานะตาม API ประวัติก่อน cutover เพราะ dispatcher ยังคงเวลาคิวและการ retry เดิม ไม่มี migration แก้คิวเดิมหรือ endpoint ส่งซ้ำใน change นี้

การกันซ้ำมีทั้ง key ของ batch และคู่เหตุการณ์กับผู้รับใน cadence เดียวกัน รวมถึงเหตุการณ์ที่อยู่ใน batch เดิมซึ่งมีผลส่ง `UNKNOWN` จึงไม่จัดเหตุการณ์เดิมส่งซ้ำในรอบถัดไป เมื่อ worker restart หรือเมื่อชุดใหม่มีเหตุการณ์เก่าปนกับเหตุการณ์ที่เข้ามาภายหลัง การ claim ใช้การอัปเดตแบบ atomic และมี lease token เพื่อไม่ให้สอง worker ส่งรายการเดียวกัน

Daily key ที่อิง activation ซึ่งยืนยันแล้วเป็น opaque `DAILY_ALERT:v2:<SHA256>` โดย identity เดิมยังคงเดิมเมื่ออนุมัติ `ADD_PARAMETER` แล้วเปลี่ยน live row ID หากพบเหตุการณ์ v1 ที่ตรง ownership, activation, policy และ episode โดยตรวจ hash เดิม จะคืน event ID เดิมเพื่อคง outbox dedup และสถานะติดตาม ก่อนเปลี่ยน backend ให้หยุด worker รุ่นเก่าเพื่อไม่ให้มี writer ต่างรุ่นแข่งสร้าง v1/v2 ระหว่าง rollout

| เหตุการณ์ | การจัดการ |
| --- | --- |
| SMTP ยอมรับทุกผู้รับ | `SMTP_ACCEPTED`; ต้องใช้ bounce/provider evidence เพิ่มถ้าต้องการยืนยันว่าถึง inbox |
| SMTP ตอบ 4xx โดยยังไม่ยอมรับผู้รับ | `RETRY_PENDING`; backoff 1, 2, 4, 8 นาที และไม่เกิน 5 attempts |
| SMTP ตอบ 5xx | `FAILED` |
| SMTP ยอมรับเพียงบางผู้รับ | `FAILED` พร้อมรายการ accepted/rejected; ไม่ส่งซ้ำทั้ง envelope |
| Timeout/ผลไม่ชัด หรือ lease หมดหลังเริ่มงาน | `UNKNOWN`; ไม่ลองใหม่อัตโนมัติเพราะอาจส่งสำเร็จแล้ว |
| ตรวจขอบเขตผู้รับไม่ได้ | retry ได้เฉพาะขั้นก่อนส่ง และจำกัด attempts เช่นเดียวกัน |
| เงื่อนไขส่งไม่ผ่าน | `SKIPPED` พร้อม `RECIPIENT_SCOPE_CHANGED`; code นี้ครอบคลุม event eligibility รวมข้อมูลรายชั่วโมงเดิมที่ไม่เกินเกณฑ์ ไม่ได้หมายถึงการเปลี่ยนอีเมลผู้รับเท่านั้น |

หากได้ `UNKNOWN` ต้องตรวจ log/provider ด้วย message ID และข้อมูลที่ปกปิดแล้วก่อนตัดสินใจดำเนินการ ไม่มี public API สำหรับ resend ในงานนี้ สถานะ SMTP แยกจาก `AUTO`, `OFFICER`, `ACKNOWLEDGED`, `DISMISSED` ของการติดตามเหตุการณ์

## ลำดับปล่อย backend

[Deployment workflow](../../../.github/workflows/deploy.yml) build และทดสอบ backend พร้อมเตรียม release และ production dependencies ก่อนหยุด service จากนั้นหยุด backend ก่อน migration `0128` เพื่อไม่ให้ API เปลี่ยน config ระหว่างเติม baseline กับติดตั้ง activation hooks แล้วตรวจ preflight, คัดลอกไฟล์ใหม่ และเริ่ม service พร้อม health check

หาก migration หรือ preflight ล้มเหลว workflow ไม่เดินต่อไปคัดลอกไฟล์ใหม่ และขั้น `always()` พยายามเริ่ม service คืน ต้องตรวจผล health และ Action log ก่อนถือว่า release สำเร็จ การเปลี่ยนลำดับนี้ไม่แก้ `.env` หรือนโยบายเปิดส่งอีเมล

หาก migration `0128` สำเร็จแล้ว แต่ preflight หรือการติดตั้งไฟล์ล้มเหลว การเริ่ม backend รุ่นเก่าคืนอาจทำให้ config เปลี่ยนโดยไม่มี activation hooks ก่อน retry ต้องหยุดการเปลี่ยน config ทวนและปรับ activation baseline ให้ตรงข้อมูลปัจจุบันโดยผู้ดูแลฐานข้อมูล แล้วติดตั้ง backend รุ่นใหม่ให้ครบก่อนเปิด worker การรัน migration ซ้ำเพียงอย่างเดียวไม่เติม baseline ใหม่ เพราะ migration ที่สำเร็จแล้วจะไม่รันอีก

## ตรวจรับก่อนเปิดสภาพแวดล้อมจริง

1. ยืนยันผู้รับหลัก สูตร 80% นโยบายวันยกเว้น และเวลาที่ข้อมูลรายชั่วโมงพร้อมก่อนกำหนด settings; ทวนเกณฑ์ค่าผิดปกติ 5 ชั่วโมงจริง โควตาวันไทย และการไม่หน่วงรอบ
2. ตรวจ migrations `0127` และ `0128` พร้อม dependency ของแหล่งค่าตรวจวัดในฐานข้อมูลทดสอบ ทวน activation baseline ของแต่ละจุด/พารามิเตอร์/หน่วย และทดสอบแก้ config, เพิ่ม/ลบ channel, legacy Test mode ที่ normalize เป็น false และอนุมัติ `ADD_PARAMETER` ห้ามใช้แหล่งข้อมูลที่อ่านไม่ได้แทน 0 รายงาน
3. ใช้ preview API ตรวจครบหกกรณีเทียบข้อความ จดหมาย ลำดับบริษัท/จุด ข้อมูลจังหวัด หน่วย และลายเซ็นกับ [แม่แบบ PDF](../api/menus/notifications/email-notifications.md#รูปแบบข้อความตาม-pdf) แต่ละคำขอต้องเป็นวันที่เดียว และกรณี 1–2 ต้องมีเวลาเริ่มตรวจวัดเดียวกัน คำขอรวมวันหรือเวลาเริ่มต่างกันตอบ `400 BAD_REQUEST` ตรวจพารามิเตอร์ชื่อเดียวกันแต่ต่างหน่วยและหลายบริษัทในช่วงเดียวกัน; วันเริ่มข้อ 4–5 ต้องอิงลำดับที่บันทึกจริงโดยไม่เดาเมื่อใช้ `PAUSE`; ข้อ 6 ทดสอบก่อน/ครบ 5 ชั่วโมง เปลี่ยนประเภทในวันเดียวกัน และต่อเนื่องถึงวันใหม่
4. รัน [ชุดจำลองอีเมลในเครื่อง](./alert-email-test.md) เพื่อดูครบหกแบบและตรวจเงื่อนไขเวลา/เกณฑ์/ส่งซ้ำ จากนั้นตรวจ SQL Server, ระบบต้นทาง และ worker จริงในสภาพแวดล้อมทดสอบ ชุดจำลองใช้ in-memory adapter และ SMTP sink ที่ `127.0.0.1` จึงยังไม่ยืนยันระบบส่วนเหล่านี้หรือ inbox production
5. ตรวจ [TDD evidence เดิม](../evidence/notifications/alert-email.tdd.md), [หลักฐานการตรวจความถูกต้องและชุดจำลอง](../evidence/notifications/alert-email-correctness.tdd.md) และ runtime `/api/v1/openapi.json` ให้ตรงกับ contract เมื่อมีการ deploy ที่ได้รับอนุญาต

ไม่เก็บ credential SMTP, database หรือ API key ในเอกสาร ไม่ใช้ log raw payload ที่มีอีเมล/ข้อมูลติดต่อเพื่อวิเคราะห์ผล
