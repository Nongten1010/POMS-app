# คู่มือล้างข้อมูลทดสอบด้วย SQL

คู่มือนี้ใช้สำหรับล้างข้อมูลทดสอบที่ทราบขอบเขตแน่นอน โดยแยกรันตามฐานข้อมูล:

- [cleanup_poms_test_data.sql](../../../backend/db/cleanup_poms_test_data.sql) สำหรับฐาน POMS หลัก
- [cleanup_parameter_test_data.sql](../../../backend/db/cleanup_parameter_test_data.sql) สำหรับฐาน Parameter

สคริปต์ทั้งสองตั้งต้นเป็น `dry run` และไม่ลบข้อมูลจนกว่าจะระบุชื่อฐานข้อมูล ยืนยันว่ามี backup และเปิดโหมด execute อย่างชัดเจน

## ขอบเขตข้อมูล

| ฐานข้อมูล | เลือกให้อัตโนมัติ | ต้องระบุเองเมื่อมี |
| --- | --- | --- |
| POMS หลัก | คำขอ `CEMS-DEMO-S0001`, `WPMS-DEMO-P0001`, จุดตรวจวัดที่มาจากคำขอเหล่านี้ และ alert ที่มี marker ของ mock seed | เลขคำขอ กวภ. หรือเลขรายงาน BOD/COD ที่สร้างทดสอบเอง รวมถึงรายการที่ผูกกับจุด demo แต่ยังไม่ได้ยืนยันว่าจะลบ |
| Parameter | ไม่มี—scope เริ่มต้นว่างเสมอ | ตารางของสถานี `S0001` และ `P0001` เฉพาะช่วง `2026-05-01`–`2026-05-10` และ `2026-06-01`–`2026-06-10` (พ.ศ. 2569) หรือสถานี/ช่วงอื่นที่ตรวจสอบแล้ว |

สคริปต์ POMS ไม่ลบข้อมูลต่อไปนี้:

- ผู้ใช้และบัญชี mock
- นิติบุคคล, factory master และ `eligible_factories`
- role, permission และข้อมูลอ้างอิง
- sequence ของเลขจุดตรวจวัด เลขคำขอเชื่อมต่อ และเลขคำขอ กวภ.
- device configuration ที่ใช้งานจริงและมี `request_id IS NULL`

การเก็บ sequence ไว้ทำให้เลขถัดไปเดินต่อจากเลขเดิมและไม่เสี่ยงออกเลขซ้ำกับประวัติ หากต้องการ reset sequence ในฐานทดสอบแยก ต้องวางแผนและตรวจสอบเลขที่เหลืออยู่ต่างหาก

> คำเตือน: seed ของ Parameter เคยค้นหา connected point จาก `point_code` เพียงอย่างเดียว หาก `S0001` หรือ `P0001` เป็นรหัสที่ใช้งานจริง ข้อมูลเดิมอาจถูก seed เขียนทับไปแล้ว ห้าม execute สคริปต์ทันที ให้หยุดตรวจประวัติและพิจารณากู้จาก backup ก่อน seed แทน

## ขั้นตอนที่แนะนำ

### 1. สำรองฐานข้อมูล

สร้าง backup ที่กู้คืนได้ของฐานที่จะล้างก่อนทุกครั้ง อย่าใช้เพียง export บางตารางแทน backup หากต้องการย้อนกลับทั้งชุด

### 2. รัน dry run

เปิดสคริปต์ใน SSMS หรือเครื่องมือ SQL Server แล้วแก้เฉพาะชื่อฐาน:

```sql
DECLARE @ExpectedDatabase SYSNAME = N'ชื่อฐานจริง';
DECLARE @Execute BIT = 0;
DECLARE @BackupConfirmed BIT = 0;
```

รันทั้งไฟล์และตรวจสอบ:

- ชื่อฐานข้อมูลถูกต้อง
- เลขคำขอ โรงงาน จุดตรวจวัด และจำนวนแถวตรงกับข้อมูลทดสอบ
- ไม่มีข้อมูลจริงปะปน
- ช่วงวันที่ Parameter ตรงกับรอบที่เคย seed
- รายการ `storage_path` ของไฟล์แนบที่ต้องจัดการภายหลัง

ผลลัพธ์ต้องลงท้ายด้วย `DRY_RUN_ROLLED_BACK` จึงถือว่ายังไม่มีการลบข้อมูล

ถ้ามีแบบ กวภ. หรือ BOD/COD ที่อ้างถึงจุด demo สคริปต์จะโชว์เป็นรายการ `blocked` และจะยังไม่ลบอัตโนมัติ เพื่อกันกรณี point demo ไปชนกับ point ที่เคยมีข้อมูลจริงมาก่อน

### 3. เพิ่มข้อมูลทดสอบที่สร้างเอง

เลข กวภ. ไม่สามารถแยกข้อมูลจริงกับข้อมูลทดสอบจากรูปแบบเลขได้ จึงต้องเพิ่มเลขที่ตรวจสอบแล้วลงใน `#TargetKwpSubmissionNos`:

```sql
INSERT INTO #TargetKwpSubmissionNos (submission_no)
VALUES ('F01-04-0001/2569');
```

ใช้วิธีเดียวกันกับ `#TargetBodCodReportNos` และ `#TargetConnectionRequestNos` ห้ามใช้เงื่อนไขกว้าง เช่น ลบทั้งปี ทั้งแบบ หรือทั้งสถานะ

ถ้าตรวจสอบแล้วว่ารายการ กวภ. หรือ BOD/COD ที่ผูกกับจุด demo เป็นข้อมูลทดสอบทั้งหมดจริง จึงค่อยเปิด flag:

```sql
DECLARE @IncludeLinkedKwpSubmissions BIT = 1;
DECLARE @IncludeLinkedBodCodReports BIT = 1;
```

ไม่ควรเปิด flag นี้ถ้ายังไม่ได้ไล่รายการ `blocked` ทีละเลข

สำหรับ Parameter ค่าเริ่มต้นของ `#TargetDateWindows` และ `#TargetParameterTables` ว่างทั้งหมด ให้คัดลอกเฉพาะตัวอย่างที่ตรวจสอบแล้วเข้าไปในทั้งสองตาราง เพิ่มช่วงวันที่แบบปิดทั้งต้นและปลาย และเพิ่มเฉพาะชื่อตารางที่อนุญาต

สคริปต์ Parameter จะลบทุกแถวของสถานี/ตาราง/ช่วงวันที่ที่อยู่ใน allow-list และรองรับความละเอียดต่ำสุดเป็นหนึ่งวันเท่านั้น จึงใช้ได้เฉพาะวันที่ที่ตรวจสอบแล้วว่าเป็นข้อมูล mock ทั้งวัน หากมีข้อมูลจริงปะปนในวันเดียวกัน ห้ามใช้สคริปต์นี้กับวันนั้น และต้องสร้าง cleanup เฉพาะกิจที่มี predicate ระดับแถวพร้อม review แยกต่างหาก

หลัง dry run ให้รวม `candidate_count` ทุกตารางและนำจำนวนที่ตรวจสอบแล้วใส่ใน `@ExpectedTotalRowsToDelete` การ execute จะหยุดทันทีหากจำนวนจริงไม่ตรงกับจำนวนนี้:

```sql
DECLARE @ExpectedTotalRowsToDelete BIGINT = 1234;
DECLARE @ParameterScopeConfirmed BIT = 1;
```

ห้ามตั้ง `@ParameterScopeConfirmed = 1` จนกว่าจะตรวจทุก station, table, date window และจำนวนแถวแล้ว หากจำนวนเปลี่ยนระหว่าง dry run กับ execute ให้หยุดตรวจใหม่ ไม่ควรแก้ expected count ให้ผ่านโดยไม่ตรวจรายการ

### 4. ลบจริง

หลังตรวจ dry run และยืนยันว่า backup ใช้งานได้แล้ว ให้แก้:

```sql
DECLARE @Execute BIT = 1;
DECLARE @BackupConfirmed BIT = 1;
```

สำหรับ Parameter ต้องตั้ง `@ParameterScopeConfirmed = 1` และ `@ExpectedTotalRowsToDelete` ให้ตรงกับ dry run ด้วย จากนั้นรันสคริปต์เดิมทั้งไฟล์อีกครั้ง สคริปต์จะลบตามลำดับ foreign key ภายใน transaction และ commit เมื่อการตรวจสอบท้ายงานผ่านเท่านั้น หากเกิดข้อผิดพลาด transaction จะ rollback

ควรรันฐาน POMS และฐาน Parameter แยกกัน พร้อมเก็บผลจำนวนแถวของแต่ละฐานไว้ตรวจสอบ

## หลังล้างข้อมูล

1. ตรวจว่ารายการคำขอ กวภ. จุดตรวจวัด BOD/COD และ alert ที่เป็น test หายไปตามจำนวน
2. ตรวจ Parameter API ในช่วงวันที่เป้าหมายว่าไม่คืนค่า mock
3. ลบไฟล์ทดสอบตาม `storage_path` เฉพาะเมื่อยืนยันว่าเป็นไฟล์ทดสอบจริงแล้ว เพราะ SQL ลบเฉพาะแถวในฐานข้อมูล ไม่ลบไฟล์บน storage
4. หลีกเลี่ยง `npm run db:seed` และ `scripts/start-and-test-api.sh` บนฐานที่เพิ่งล้าง เพราะคำสั่งดังกล่าวสามารถสร้าง demo data กลับมาได้

ชุดทดสอบโครงสร้างความปลอดภัยของสคริปต์อยู่ที่ [test-data-cleanup-sql.test.ts](../../../backend/tests/unit/test-data-cleanup-sql.test.ts)
